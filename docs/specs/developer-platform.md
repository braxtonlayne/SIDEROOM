# Developer platform (applications, bots, OAuth2, commands, interactions)

Status: backend built on `feat/p8-dev-be` (extended in p11 to p13) (inventory DEV-APP, DEV-BOT, DEV-SDK backend parts). Governing docs: [11](../11-extensibility-and-developer-platform.md), [05](../05-api-and-gateway.md), [07](../07-permissions-and-staff.md), open question 56. The web side (developer portal, consent screen, command picker) is coded against section 3 of this file.

This file has two parts: how the platform behaves (1 and 2) and **HTTP API as built** (3), the contract the web agent codes against. Paths are relative to `/api/v1` (`/api/v10` is an alias). Every id is a snowflake string. Timestamps are ISO8601. Errors use the Discord body `{code, message, errors?}`; OAuth2 token endpoints use the RFC 6749 body (section 3.7).

## 1. Model

* **Developer** = an account with the `APP_DEVELOPER` flag (`accounts.flags` bit 1). Any member can apply (`POST /developers/apply`); staff holding `REVIEW_APPS` approve or reject. Doc 11 section 2.1 lets people create applications before approval, so the flag is a trust marker and gates nothing in this phase except the staff list.
* **Application** (`applications`): owned by one account (no teams: the docs do not specify them, so they are not built). Creating an application also creates its **bot account**: a row in `accounts` with `is_bot = true`, an unusable password hash, a synthetic address `bot-<id>@bots.invalid`, and username `bot_<snowflake>`. The display name (`global_name`) is the application name. Bot accounts never count toward the account cap (D-013), never log in (no password verifies, `POST /sr/auth/login` answers like any wrong password) and cannot be registered over.
* **Release state** (`release_state`): `development` (default), `in_review`, `released`, `suspended`.
  * `development`: the bot can be installed only by the **owner**, into a guild where the owner holds `MANAGE_GUILD` (or owns it) and which has **25 members or fewer** (doc 11 section 2.1). Any other install is refused with `900120` (HTTP 403, "App not released").
  * Owners submit a **version** (`POST /applications/{id}/versions`) which snapshots the manifest (name, description, scopes, redirect URIs, requested privileged intents, command list, URLs) and moves the application to `in_review`. A staff decision (`REVIEW_APPS`) approves it (`released`; the approved intents are set by the reviewer) or rejects/asks for changes (back to `development`, or stays `released` for later versions). A later version that changes scopes, redirect URIs or requested intents is flagged `needs_review` with the reason; the diff against the previously approved manifest is returned on every version.
  * `suspended` (staff action): bot tokens and OAuth tokens stop authenticating, the gateway refuses IDENTIFY for the bot, new interactions are refused. Nothing is deleted; `unsuspend` restores the previous state.
* **Bot public flag** (`bot_public`): when false only the owner may add the bot to a server (even when released). `bot_require_code_grant` is stored and returned but only informational (the authorize flow always returns a code when a `redirect_uri` is given).
* **Privileged intents.** `GUILD_MEMBERS` (1<<1), `GUILD_PRESENCES` (1<<8), `MESSAGE_CONTENT` (1<<15). The developer toggles `intents_requested` on the bot settings. What the gateway allows on IDENTIFY: in `development` the requested set (test servers only, so low risk); in `released` only `requested AND approved` (staff approve with a version decision). IDENTIFY with a bit outside the allowed set closes with `4014`. The application `flags` field reports Discord's `GATEWAY_*` / `GATEWAY_*_LIMITED` bits accordingly.
* **Credentials** (all random, all stored as SHA-256 hashes with a per-kind domain label; raw values are shown once):

  | Credential | Format | Stored | Where it works |
  |---|---|---|---|
  | Bot token | Discord shape `base64url(bot user id).base64url(issued unix s).base64url(32 random bytes)` (open question 56) | `bot_tokens.token_hash`, `revoked_at` | `Authorization: Bot <token>`, gateway IDENTIFY `token` (without the `Bot ` prefix, as Discord libraries send it). One live token per application: a reset revokes the old one. |
  | Client secret | 43-char base64url (256 bits) | `applications.client_secret_hash` | `/oauth2/token`, `/oauth2/token/revoke`, `/oauth2/introspect` client authentication |
  | OAuth2 authorization code | 43 chars, 5 minutes, single use | `oauth2_codes.code_hash` | `/oauth2/token` |
  | OAuth2 access / refresh token | 43 chars each; access 7 days, refresh 90 days, refresh tokens rotate | `oauth2_tokens.access_hash`, `refresh_hash` | `Authorization: Bearer <token>`; refresh at `/oauth2/token` |
  | Interaction token | 43 chars, valid 15 minutes | `interactions.token_hash` | `/interactions/{id}/{token}/callback`, `/webhooks/{application_id}/{token}[/messages/...]` |

  Hash lookups go through a unique index on the digest and the stored digest is compared again in constant time before a match is accepted. Secrets never appear in `Debug`, logs or audit rows. Credentials also die with their accounts: an OAuth2 token stops working when the user is not `active` (banned, deactivated, deleted), a bot token when the bot account or the application's owner is not `active`, and everything of a suspended application stops at once.
* **Install** (`application_installs`, one row per application and guild): created by the authorize flow. With the `bot` scope the bot account joins the guild with a **managed role** (`managed = true`, `tags.bot_id`) that holds the granted permissions. Granted permissions = requested `permissions` AND the installer's own guild permissions (an installer without `ADMINISTRATOR` cannot hand out `ADMINISTRATOR`, or anything else they lack); this is stricter than Discord on purpose (no privilege escalation). An `audit_log_entries` row `BOT_ADD` (28) is written, `GUILD_MEMBER_ADD` and `GUILD_ROLE_CREATE` are dispatched, and the application's audit trail records the install. `applications.commands` without `bot` installs the commands only (no member).
* **Authorization policy (who may call what)**, enforced centrally in the `Principal` extractor, not per handler:
  * **Session** (browser cookie + `X-SR-CSRF`): everything for the signed-in user. Owner-only operations (create/modify/delete applications, reset secret/token, versions, the authorize POST) accept sessions only; bots, bearers and anyone else get `20001`/`50001`.
  * **Bot** (`Authorization: Bot`): the Discord-compatible bot routes. Denied outright (`20001`, HTTP 403): `/admin/*`, `/developers/*`, `/sr/auth/*`, `/oauth2/authorize`, owner-only `/applications` management routes, user-account routes (`/users/@me/settings`, `/users/@me/relationships*`, `/users/@me/notes`...). A bot can only ever act with the guild/channel permissions of its roles; every route re-checks them.
  * **Bearer** (`Authorization: Bearer`): default deny. Only these routes accept it: `GET /users/@me` (`identify`; the `email` field needs `email`), `GET /users/@me/guilds` (`guilds`), `GET /oauth2/@me`, `PUT /applications/{id}/guilds/{guild_id}/commands/permissions` and `.../{command_id}/permissions` (`applications.commands.permissions.update`). Everything else answers `50001` "Missing Access".
  * The policy is the `ApiSettings.enforce_credential_policy` switch: on for the production wiring (`ApiSettings::for_public_url`), off in the `Default` the unit-test fixtures use (they stand bot tokens in for users). `crates/sr-api/src/auth/policy.rs` holds the two route lists and their tests.
* **Logs and memory.** Request logs mask the token segment of `/interactions/{id}/{token}/callback` and `/webhooks/{id}/{token}`; types that hold a raw secret have a `Debug` that prints nothing of it; `INTERACTION_CREATE` (which carries the interaction token) travels only on the bot user's own topic and is never persisted.

## 2. Compatibility with Discord

Compatible: the application, user, member, role and message object shapes used here; bot token format and `Authorization: Bot`; gateway IDENTIFY/READY/RESUME, privileged-intent close codes `4013`/`4014`, `GET /gateway/bot`; application command objects, option types 1-11, command limits (100 chat-input, 15 user, 15 message commands per application and scope, 200 command creations per application, guild and day is **not** enforced), bulk overwrite, command permissions v2 semantics; interaction types 2-5 and callback types 4-9 (type 1 PONG accepted, 12 refused); `INTERACTION_CREATE` payload; ephemeral flag `64`; `/interactions/{id}/{token}/callback`; `/webhooks/{application_id}/{token}` follow-ups and `/messages/@original|{id}`; the 3 second initial-response window and the 15 minute token life; OAuth2 authorization code flow with PKCE (`S256`), `state`, `identify`/`email`/`guilds`/`bot`/`applications.commands` scopes, `/oauth2/token`, `/oauth2/token/revoke`, `/oauth2/@me`; `X-RateLimit-*` headers and the global 50 requests per second per bot.

Different or missing (see also doc 05 section 7):

* Teams, role connections, monetization/SKUs: not built. Activities (`DEV-ACT-*`) are built as reviewed bundles (section 3.10). Application emoji are managed in the portal or with the application's bot token and used by that bot (section 3.9, D-237); Rich Presence assets are managed in the portal only and no client renders them yet.
* **Webhook execution (p13).** `POST /webhooks/{id}/{token}` takes `username` (1 to 80 characters), `avatar_url` (https, at most 512 characters), `wait` and `thread_id` (a thread of the webhook's channel). The message is shown as the webhook: `author.id` and `webhook_id` are the webhook id, `author.username` is the override or the webhook name, `author.bot` is true and `author.avatar_url` is an image-proxy path of the override (never the raw URL). `messages.author_id` stays the webhook's creator, whose channel permissions applied when sending; the display data is `message_webhook_authors`. `authorType:webhook` search and `thread_name` for forum channels are not built.
* **Attachment options (p13).** A command option of type 11 takes an upload slot id the invoker staged in the channel (`POST /channels/{id}/attachments`, PUT, complete). `POST /interactions` completes the slot when the client did not, refuses slots of someone else, of another channel or already on a message (`50035`), and the bot receives `data.resolved.attachments[id] = {id, filename, size, content_type, url (signed, 24 hours), width, height, ...}`. The web command form uploads the chosen file first. The typed `name:value` composer syntax does not take files.
* **SDKs (p13).** `crates/sr-sdk` (Rust) and `packages/bot` (`@sideroom/bot`, TypeScript) wrap REST, gateway shards, a cache and a command framework; see the Bot SDKs page in the portal docs. Neither offers voice: bots in voice need MLS, which is not built.
* HTTP interactions endpoint (p11): `PATCH /applications/{id}` takes `interactions_endpoint_url` (https, verified before saving with a signed PING answered `{"type":1}` and a wrong-signature PING refused with 401). `POST /applications/{id}/interactions-key` creates the Ed25519 key (idempotent); the owner view shows `verify_key` (hex). Requests carry `X-Signature-Ed25519` and `X-Signature-Timestamp` over timestamp + body; the reply body is the callback body (`{type, data}`), applied within the 3 s window. With a URL set, `INTERACTION_CREATE` is no longer sent over the gateway. Targets must be public addresses (sr-net policy); the private seed is sealed with `server.secret_key` (`applications.interactions_signing_seed_sealed`, D-185; the plaintext column of migration 0710 is emptied by the startup job `apps.seal_seeds`) and never returned. **Auto-disable (D-186):** every delivery outcome is counted; 25 consecutive failures (transport error, non-200 or unreadable reply) within 10 minutes set `endpoint_state = disabled`, interactions fall back to the gateway, and the owner gets a system DM. The owner view shows `interactions_endpoint_state`; `POST /applications/{id}/endpoint/verify` runs the PING check against the saved URL and re-enables. Saving a URL also starts healthy.
* **App testers (D-204).** `GET|POST /applications/{id}/testers` (owner; body `{username}` or `{user_id}`), `DELETE /applications/{id}/testers/{account_id}`; at most 25 rows per application (invited and accepted together, 409 beyond). An invitation is a system DM with buttons `sr:tester-accept:<id>` and `sr:tester-decline:<id>` that call `POST /developers/tester-invites/{id}/respond {accept}` (invitee only; declining deletes the row and blocks a new invitation to that account for 24 hours: `900122` `TESTER_RECENTLY_DECLINED` (409); the hourly `apps.housekeeping` job forgets older declines, G-84). An accepted tester may install a `development` application (also a private one) where they hold `MANAGE_GUILD`, still only in guilds of at most 25 members (900120 otherwise). Testers count only while the application is in `development`.
* Sharding (p11): IDENTIFY `shard` is `[id, count]`, count 1..1024, id < count (else `4010`). A shard gets the guilds where `(guild_id >> 22) % count == id`; user-addressed events follow their `guild_id`, others go to shard 0. `GET /gateway/bot` recommends one shard per 1000 installs.
* Web client helpers (p11): `GET /channels/{id}/application-commands` returns `{applications, application_commands}` the caller may use there (session only); `POST /interactions` type 3 may omit `application_id` (taken from the message author's bot).
* Installs: only server installs. `guilds.join`, `guilds.members.read`, `connections`, `webhook.incoming`, `rpc*`, `sr.*` scopes are rejected with `invalid_scope`. Redirect URIs must be `https`, or `http` on `localhost`/`127.0.0.1`/`[::1]`; custom schemes are refused. Only `response_type=code`; no implicit grant, no `client_credentials`.
* Interaction responses: a non-ephemeral response is a normal message sent **as the bot**, so it needs the bot's own `SEND_MESSAGES` (and the other send permissions) in the channel; Discord lets the token bypass this. Ephemeral messages are never stored: they are dispatched to the invoking user's sessions only (`MESSAGE_CREATE`/`MESSAGE_UPDATE` with flag 64) and kept 15 minutes so the bot can edit them. A deferred response (`5`, `6`) shows "is thinking" to the invoking user only (via `INTERACTION_SUCCESS`); other members see the message when the bot posts it. Interactions work in servers only (no DM or user installs).
* Components: buttons only (custom_id/style/label/url/disabled), as far as the existing message model stores them. Select menus and modal text inputs pass through the interaction payload (`values`, modal `components`) but the stored message model does not keep select options. Modals are delivered to the invoking user as `INTERACTION_MODAL_CREATE`.
* Editing a **posted** interaction message (`PATCH .../messages/{id}`, callback type `7`) changes its `content` and the `SUPPRESS_EMBEDS` flag only: the message store has no embed or component replacement yet, so a body with `embeds` or `components` is refused with `50035` (`UNSUPPORTED`) rather than silently ignored. Ephemeral messages are kept as a whole object and can be replaced completely. Creating a message (callback `4`, follow-ups, the first edit after a deferral) takes embeds and components.
* Message `interaction` metadata and `application_id` on messages are not stored.
* Autocomplete results reach the invoking client as the SIDE ROOM dispatch `SR_INTERACTION_AUTOCOMPLETE {id, nonce, choices}` (Discord returns them in the HTTP response of the client's own request).
* Rate limiting is per credential and per route bucket like the rest of the API; there is no "invalid request" ban counter.
* Bot token reset does not disconnect running gateway sessions of the old token; they end at the next reconnect (a revoked token cannot IDENTIFY or RESUME).

## 3. HTTP API as built

Auth column: **S** = browser session (CSRF on writes), **B** = bot token of the named application, **U** = user bearer token, **St** = staff session with the platform permission shown, **-** = none. "Owner" means the application's `owner_id`; anyone else gets `10002 Unknown Application` (404, the same answer as a missing id, so ids cannot be probed).

### 3.3 OAuth2 and installs

| Method and path | Auth | Request | Response |
|---|---|---|---|
| `GET /oauth2/authorize?client_id&scope&redirect_uri?&response_type=code&state?&code_challenge?&code_challenge_method=S256&permissions?&guild_id?` | S | query | Consent screen data: `{application:{id,name,icon,description,bot_public,release_state,privacy_policy_url,terms_of_service_url}, bot:BotUser\|null, scopes:[{name,description}], redirect_uri\|null, state, user:{id,username,global_name}, guilds:[{id,name,icon,owner,permissions,can_install,reason?}], permissions:"<bits>", already_authorized: bool}`. `guilds` is only filled when `scope` has `bot` or `applications.commands`; `can_install` is true only with `MANAGE_GUILD` (or owner) and, in `development`, only for the owner in a guild with <=25 members (`reason`: `"missing_permission"`, `"app_not_released"`, `"bot_not_public"`). An unknown client, a redirect URI that is not registered or an invalid scope is a **400 JSON error, never a redirect** |
| `POST /oauth2/authorize` | S | `{client_id, scope, redirect_uri?, response_type:"code", state?, code_challenge?, code_challenge_method?, permissions?, guild_id?, authorize: bool}` | `{location}`: the URL to send the browser to. Approve: `redirect_uri?code=…&state=…&guild_id=…`, or `/oauth2/authorized` when there is no redirect URI. Deny (`authorize:false`) with a valid redirect: `redirect_uri?error=access_denied&state=…`. With `bot`: `guild_id` is required, the caller must hold `MANAGE_GUILD` there; the install (3.2 model) happens before the redirect. 403 `50013` without the permission, 403 `900120` for an unreleased app, 403 `50001` for a private bot of someone else. A bot that is already in the guild is not an error: the install is refreshed (the managed role gets the new permissions) and the answer carries `already_installed: true` (only present for `bot` installs) |
| `POST /oauth2/token` | client auth | form or JSON: `grant_type=authorization_code` with `code`, `redirect_uri`, `code_verifier?`; or `grant_type=refresh_token` with `refresh_token`. Client auth: HTTP Basic `client_id:client_secret`, or `client_id`/`client_secret` in the body. A request with no secret is accepted only for a code that was issued with a `code_challenge` and carries the matching `code_verifier` | `{access_token, token_type:"Bearer", expires_in, refresh_token, scope}` (space-separated). Errors per RFC 6749 (3.7). 30 requests/min per client and per address |
| `POST /oauth2/token/revoke` | client auth | `{token, token_type_hint?}` (form or JSON) | 200 `{}` for any input (RFC 7009); only tokens of the authenticated client are revoked |
| `POST /oauth2/introspect` | client auth | `{token, token_type_hint?}` | RFC 7662: `{active:false}` or `{active:true, scope, client_id, username, sub, exp, iat, token_type:"Bearer"}`; only the issuing client may introspect its tokens (others get `{active:false}`) |
| `GET /oauth2/@me` | U | | `{application: Application(public), scopes[], expires, user?:UserObject}` (`user` needs `identify`) |
| `GET /oauth2/tokens` | S | | `[{id, application:{id,name,icon}, scopes[], created_at}]` the apps the user authorized |
| `DELETE /oauth2/tokens/{grant_id}` | S | | 204; revokes the grant and every token of it. Does not remove an installed bot |

Redirect URI rules: absolute, `https`, or `http` for `localhost`, `127.0.0.1`, `[::1]`; no fragment, no userinfo, <=512 chars. Matching at authorize and token time is an exact string comparison against the registered list.

PKCE: only `S256`. If a `code_challenge` was sent the verifier is mandatory at the token endpoint and compared in constant time (`BASE64URL(SHA256(verifier))`, verifier 43-128 chars of `[A-Za-z0-9-._~]`).

Code and refresh handling: a used code presented again revokes every token minted from it. A used refresh token presented again revokes the whole grant (rotation reuse detection).

`GET /users/@me` for a bearer returns `id`, `username`, `global_name`, `avatar`, `bot:false` (+ `email` and `verified` with the `email` scope); `GET /users/@me/guilds` needs `guilds`.

### 3.4 Gateway for bots

* `GET /gateway/bot` (B): `{url:"wss://<host>/gateway", shards:1, session_start_limit:{total:1000, remaining:1000, reset_after, max_concurrency:1}}`.
* IDENTIFY with a bot token: `intents` is required; unknown bits close `4013`; privileged bits not allowed close `4014`; `shard` other than `[0,1]` closes `4010`. READY carries `user` (with `bot:true`), `application:{id, flags}`, `guilds` (unavailable stubs) as usual.
* Message events: without `MESSAGE_CONTENT` the bot receives `content`, `embeds`, `attachments`, `components` and `poll` blanked, except for DMs, messages that mention it and its own messages (doc 05 section 6.2).
* `INTERACTION_CREATE` is delivered to the bot user's sessions (no intent needed). `GUILD_CREATE` follows an install.

### 3.5 Application commands (B, `application_id` must be the token's application, or `@me` is **not** accepted)

Global: `GET/POST/PUT /applications/{app}/commands`, `GET/PATCH/DELETE /applications/{app}/commands/{id}`. Guild: the same under `/applications/{app}/guilds/{guild}/commands[...]`; the application must be installed in the guild (else `50001`). `GET` takes `with_localizations=true`.

Command body: `name` (chat input: 1-32 of lowercase letters/digits/`-`/`_`; user/message commands 1-32 with spaces and capitals allowed), `type` (1 chat input default, 2 user, 3 message), `description` (chat input 1-100; user/message must be empty), `options` (<=25; types 1-11; sub-command nesting max two levels: group > sub-command > options; required options first; <=25 choices; choices and `autocomplete` are mutually exclusive; `min_value`/`max_value`, `min_length` 0-6000, `max_length` 1-6000, `channel_types`), `name_localizations`/`description_localizations` (locale to string, same length rules), `default_member_permissions` (bit string or null), `dm_permission` (accepted, stored; no DM interactions yet), `nsfw`, `contexts`, `integration_types` (stored). The serialized command may not exceed 8000 characters. `POST` with an existing name and type updates it (200, else 201). `PUT` replaces the whole set for that scope in one transaction and returns it; ids of unchanged names are kept. Limits per scope: 100 chat-input, 15 user, 15 message commands. Errors use `50035` field trees (`options.0.name`...) and "too many commands" as `50035` on `name` (code `MAX_APPLICATION_COMMANDS`).

Command object: `{id, application_id, version, default_member_permissions, type, name, name_localizations, description, description_localizations, guild_id?, dm_permission, options?, nsfw, contexts, integration_types}`.

Permissions v2: `GET /applications/{app}/guilds/{guild}/commands/permissions` and `.../{command_id}/permissions` (B of that application) return `{id, application_id, guild_id, permissions:[{id, type (1 role, 2 user, 3 channel), permission: bool}]}`; `PUT .../{command_id}/permissions` `{permissions:[...]}` (<=100 entries) needs a **bearer token** with `applications.commands.permissions.update` of a user holding `MANAGE_GUILD` in the guild (bot tokens and sessions are refused, as on Discord). Evaluation when a member invokes a command (see 3.6), in this order: the invoker needs `USE_APPLICATION_COMMANDS` in the channel; `ADMINISTRATOR` (and the server owner) always pass; the command's own overwrites replace the application-wide ones (command id = application id) when it has any; a channel entry (the channel id, or `guild id - 1` for all channels) that denies blocks; then an entry for the user decides; else the entries of the member's roles (any allow wins); else the `@everyone` entry (role id = guild id); with no applicable entry `default_member_permissions` decides (`null` = everyone, `0` = administrators only).

### 3.6 Interactions

| Method and path | Auth | Request | Response |
|---|---|---|---|
| `POST /interactions` | S (the member using the app) | `{type: 2\|3\|4\|5, application_id, channel_id, guild_id?, nonce?, data}` | 204. Validates membership, channel visibility, `USE_APPLICATION_COMMANDS`, install, the command and its permissions, option types against the registered schema, then creates the interaction and dispatches `INTERACTION_CREATE` to the bot user's sessions. 400 `50035`, 403 `50001`/`50013`, 404 `10063` unknown command |
| `POST /interactions/{id}/{token}/callback` | token | `{type, data?}` | 204. Within 3 s of creation, once. 404 `10062` after the window or for an unknown id; 400 `40060` if already acknowledged; 401 `50027` for a wrong token |
| `GET /webhooks/{application_id}/{token}/messages/@original` | token | | the original response message (non-ephemeral: the stored message; ephemeral: its saved payload) |
| `PATCH /webhooks/{application_id}/{token}/messages/@original` or `/{message_id}` | token | `{content?, embeds?, components?, flags?}` | message; for a deferred interaction the first edit **creates** the original |
| `DELETE /webhooks/{application_id}/{token}/messages/@original` or `/{message_id}` | token | | 204 |
| `POST /webhooks/{application_id}/{token}?wait` | token | `{content, embeds, components, flags (64 = ephemeral), tts}` | follow-up message (204 or 200 with `wait=true`). The existing webhook-execute route detects an interaction token first. Tokens work for 15 minutes; only messages that belong to the interaction can be edited or deleted |

Interaction types a user client may create: `2` application command (`data: {id, name?, type?, options?, target_id?}`; `name`/`type` are taken from the stored command, the client's copy is ignored), `3` message component (`data: {custom_id, component_type, values?}`, `message_id` required; the message must be in the channel), `4` autocomplete (`data` like type 2 with one option `focused: true`), `5` modal submit (`data: {custom_id, components}`).

Callback types: `4` message with source, `5` deferred message, `6` deferred update (components only), `7` update message (components only), `8` autocomplete result (`data.choices`, <=25), `9` modal (`data: {custom_id, title (<=45), components}`), `1` pong. Callback `data` message fields: `content` (<=2000), `embeds` (<=10), `components`, `flags` (only `64` and `4` are honoured), `tts`.

Gateway payload to the bot (`INTERACTION_CREATE`): `{id, application_id, type, data, guild_id, channel_id, channel:{id,type}, member:{user, roles[], permissions, joined_at, nick, pending, flags}, token, version:1, message? (components), app_permissions, locale:"en-US", guild_locale, entitlements:[], context:0}`. `data.resolved` carries `users`, `members`, `roles`, `channels` for user/role/channel/mentionable options.

Client-facing dispatches to the invoking user's sessions: `INTERACTION_SUCCESS {id, nonce}` (the bot acknowledged: responded or deferred), `INTERACTION_FAILURE {id, nonce, reason_code: 2}` (no acknowledgement in 3 s), `INTERACTION_MODAL_CREATE {id, nonce, application_id, channel_id, guild_id, custom_id, title, components}`, and for ephemeral output `MESSAGE_CREATE`/`MESSAGE_UPDATE`/`MESSAGE_DELETE` addressed to that user only (flags 64, `id` is a fresh snowflake, `channel_id`, `author` the bot).

### 3.7 Errors

New codes: `10062` Unknown interaction (404), `10063` Unknown application command (404), `40060` Interaction has already been acknowledged (400), `50027` Invalid webhook token (401), `900120` App not released (403), `900121` Application suspended (403). Existing: `10002` Unknown Application, `20001` Bots cannot use this endpoint, `50001`, `50013`, `50035`, `900004` re-auth, `900010` conflict.

OAuth token endpoint errors (`/oauth2/token`, `/revoke`, `/introspect`): HTTP 400 (401 with `WWW-Authenticate: Basic` for `invalid_client` when Basic auth was tried) and `{"error": "invalid_request"|"invalid_client"|"invalid_grant"|"unauthorized_client"|"unsupported_grant_type"|"invalid_scope", "error_description": "..."}`.

### 3.8 Rate limits

All routes share the global `X-RateLimit-*` machinery: 50 requests per second per credential (each bot token is its own identity), `X-RateLimit-Global: true` and `X-RateLimit-Scope: global` on a global 429, `Retry-After`. Extra buckets: `POST /oauth2/token` 30/min per client id and 30/min per address, `POST /oauth2/authorize` 20/min, `POST /interactions` 20/10 s per user, `POST /interactions/{id}/{token}/callback` 5/5 s, `POST /applications` 5/hour per owner, `POST /developers/apply` 3/day. Secrets and token resets 5/hour per application.

### 3.9 Application emoji, Rich Presence assets, App Directory (p13)

Emoji routes take the owner's session or the bot token of that application (D-237; another application's bot gets 403 `50001`); everything else here is owner session only (bots get `20001`, bearers `50001`), except `GET /applications/{id}/assets`, which any signed-in session may read. Images go up as `data:` URIs; the server sniffs the type, shrinks them and stores them under `emoji/app/{application}/{id}.{ext}` and `emoji/app-assets/{application}/{id}.{ext}`. Objects carry `url`, a short-lived signed CDN path for the portal.

**Using application emoji (D-237).** `<:name:id>` / `<a:name:id>` of an application emoji renders in messages and interaction responses sent by that application's bot; in anyone else's message the message object lists the id in `sr_text_emoji` and clients show `:name:` text. `GET /sr/emojis/{id}` and `/url` resolve application emoji for any session after server emoji; the info object carries `application: {id, name, icon}` and `guild: null` (the popout says "Emoji of <application>" and offers no join).

**App Directory (DEV-BOT-012).** Any signed-in session (not a bot): `GET /app-directory?query=&tag=&page=&per_page=` lists `released`, non-suspended applications whose `bot_public` is true, most installed first (`{items:[{id, name, description, icon, bot_id, tags, installs}], has_more}`; `per_page` at most 50, `query` at most 100 characters, matched case-insensitively against name, description and tags with `%`/`_` literal; `tag` is exact). `GET /app-directory/tags` returns `[{tag, count}]` (at most 30, the categories). `GET /app-directory/{id}` is the app page: the list fields plus `terms_of_service_url`, `privacy_policy_url`, `install_scopes`, `install_permissions` and the global `commands` (name, description, type; at most 100). "Add App" is the ordinary authorize flow (`/oauth2/authorize?client_id&scope&permissions&guild_id`) with the application's own install parameters; the web client offers it in Server Settings, Integrations, Bots and Apps for people with Manage Server. The categories are the applications' tags (up to 5 per application, set in the portal): there is no separate category field.


### 3.10 Activities (p14, DEV-ACT-001 to 004; bundles J-12, D-246 to D-248)

Off unless `[activities] enabled = true` (default false; env `SR_ACTIVITIES__ENABLED`). Everything but the owner's settings answers 404 `SrNotFound` ("Activities are not enabled on this server.") when off, `GET /activities` and `GET /channels/{id}/activity` answer `enabled: false`, and the proxy host answers 404. The wildcard host, its DNS-challenge certificate, the CSP `frame-src` and `VITE_ACTIVITIES_ENABLED` are the operator's part (`deploy/compose/caddy/activities.snippet`, doc 12 step 1, OQ-XC-3).

An Activity is **an uploaded bundle that sr-server hosts**, reviewed by staff by its SHA-256 and served from the Activity's own origin. The entry URL of the first slice survives only as a development-mode live URL (D-247).

* **Bundles (owner session).** `POST /applications/{id}/activity/bundles` takes the zip itself as the request body (`application/zip`; the chat attachment slots the brief for this item mentions belong to a channel, so a direct upload route is used) and answers `201 {bundle, entries[{path, size, content_type}]}`. Limits and rules, all checked before anything is stored and each refusal naming the entry (`400`, field `bundle`): at most 32 MiB unpacked (counted while inflating, never trusted from headers) and 2,000 entries; entry names use `/` and `A-Za-z0-9 . _ - ~ @ +` only (no absolute path, drive letter, backslash, `.` or `..` segment, empty segment, hidden segment starting with `.`, percent-encoding or control character; at most 256 characters, 128 per segment); regular files and directories only (symbolic links, devices and encrypted entries are refused); names that differ only in case, or a file that is also a directory, are refused; every file's extension must be in the allow-list `html js mjs css json map wasm png jpg jpeg webp gif svg ico woff2 mp3 ogg webm txt` (the content type is derived from the extension at serve time); `index.html` at the root. A zip must start at byte 0. The bundle is a `draft`; earlier drafts and rejected bundles become `superseded`; the same zip again returns the same bundle. Files are unpacked to object storage under `activities/<application_id>/<sha256>/<path>` (the zip itself at `activities/<application_id>/<sha256>.zip`, for the reviewer). `GET .../activity/bundles/{bundle_id}` lists a bundle's files. Table `application_activity_bundles` (migration 0965): `id, application_id, sha256, byte_size, entry_count, manifest, uploaded_at, state draft|pending|approved|rejected|superseded, reviewed_by, reviewed_at, note`.
* **Settings and review.** `GET|PUT /applications/{id}/activity` hold `dev_entry_url` (https; accepted only while the application is in `development`) and up to 10 `url_mappings` `{prefix, target}` (prefix `/api`-style, never `/`; target https, no query). The reply carries `origin` (`https://<application-id>.activities.<host>`), `implicit_redirect_uri` (`<origin>/` once the application has an Activity: it is accepted as a redirect URI without being stored, J-13, D-248, and the OAuth2 tab lists it read-only as "Activity (automatic)"), `enabled`, the summary `review_state` (`pending` while a bundle waits, else `approved` while a bundle is reviewed, else `rejected` / `draft`), `reviewed_bundle` and the recent `bundles`. `POST .../activity/submit {bundle_id}` moves a `draft` to `pending` (an earlier pending bundle is superseded; an approved bundle keeps being served until staff decide). Staff with `REVIEW_APPS`: `GET /admin/developers/activities` (queue: each entry carries the bundle's hash, size and files), `GET /admin/developers/activities/{application_id}/bundles/{bundle_id}/download` (the zip, logged as `developer.activity_download`), `POST /admin/developers/activities/{application_id}/decision {decision: approve|reject, bundle_id, note}`; a decision about a bundle that is not the pending one is refused (409). Approving supersedes the previously approved bundle and sets `reviewed_bundle_id`. **A change to the URL mappings withdraws the approval** (the reviewed bundle is superseded, the Activity is paused until a new bundle is approved); a new upload does not touch the reviewed bundle until it is approved. Decisions are written to the staff access log (`developer.activity_decision`, with the bundle hash). Superseded bundles' objects are deleted by the hourly `activities.gc` job.
* **Release condition (D-246).** An approved bundle is served, listed in the shelf and startable only while the application is `released` and not suspended. A `development` application with a `dev_entry_url` is served live and unpinned, listed and startable only for its owner and accepted testers, and only in guilds of at most 25 members (D-204); an instance running a development build says `development: true` and the panel shows "Development". A suspended application is neither served nor listed.
* **Proxy (DEV-ACT-001).** A request whose `Host` is `<application-id>.activities.<public host>` is answered by sr-server (`routes::activities::proxy`, outermost layer, before any route). **The proxy serves only the reviewed bundle**: `/` is its `index.html` (`Cache-Control: no-cache`), a path ending in `/` is the `index.html` there, any other path is that file of the bundle (`Cache-Control: public, max-age=3600`; `immutable` is not used because paths carry no hash), with the content type from the extension. Request paths pass the same rules as zip entries (so `..`, `.`, encoded slashes or dots, backslashes, hidden segments and control characters are 400 and never looked up); a file that is not in the bundle is 404. The Activity is served and startable outside development while the application has been released at least once and is not suspended (`released`, or `in_review` with a prior release; D-252); a suspension stops it at once. With no reviewed bundle (never approved, withdrawn, or the application never released) the host answers 503 "paused until reviewed again". For a `development` application the entry document and other files come live from `dev_entry_url` (through the SSRF-safe client) with the response header `X-SR-Activity-Mode: development`. A path under a mapping prefix is fetched from the mapping's target (longest prefix, whole segments, the target's own path prefix kept). **Methods:** `GET` and `HEAD` for everything; `POST`, `PUT`, `PATCH` and `DELETE` only under a mapping prefix (J-17, D-248): never for the shell or the bundle (405 `Allow: GET, HEAD`), body at most 1 MiB (413 beyond, also from `Content-Length`), only `Content-Type` and the body are sent, redirects are not followed, the answer comes back with its status when 2xx or 4xx (anything else is 502) and only its `Content-Type`; a browser `Origin` other than the Activity's own is 403. Fetches use `sr-net`'s `SafeClient` (public addresses; GET follows at most 3 validated redirects, 8 MiB). The application's headers and cookies never reach the browser. Every response carries `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; media-src 'self' blob:; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors <app origin>`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and a `Permissions-Policy` that turns camera, microphone, geolocation, payment, usb, display-capture and clipboard off (fullscreen on).
* **Instances (DEV-ACT-002, J-15, J-16).** Tables `activity_instances` (one running per channel, partial unique index; `channel_type voice|text`) and `activity_participants`. `GET /activities` is the shelf `{enabled, items[{application_id, name, description, development}]}`. `POST /channels/{id}/activity {application_id}` starts an Activity in a guild **voice** channel (`VIEW_CHANNEL`, `CONNECT` and `USE_EMBEDDED_ACTIVITIES` there) or guild **text** or announcement channel (`VIEW_CHANNEL` and `USE_EMBEDDED_ACTIVITIES`; no `CONNECT`); a direct message channel and other channel types are refused; 409 when one is running; 404 for an application that is not startable (see the release condition). The starter is its first participant. `GET /channels/{id}/activity` is `{enabled, instance|null}`; `GET /activity-instances/{id}`; `POST .../join` (same permissions); `POST .../leave` (the last participant leaving ends it); `DELETE /activity-instances/{id}` (starter, or `MANAGE_CHANNELS`). Instance object: `{id, application_id, application_name, guild_id, channel_id, channel_type, development, started_by, created_at_ms, participants[{user_id, joined_at_ms}]}`. Gateway: `SR_ACTIVITY_INSTANCE_UPDATE {channel_id, instance|null}` (user-scoped, to everyone who can see the channel). **In a voice channel participants follow the call:** the server listens to the voice events (`VoiceLeft`, which the gateway publishes once a voice state is removed, after its own session grace period) and removes the member from the Activity running in that channel; a rejoin of the same channel within 5 seconds is not a leave; the last removal ends the instance and dispatches `instance: null`. A text-channel Activity is not tied to a call. Explicit "Leave" stays.
* **Embedded App SDK (DEV-ACT-003, J-14).** `packages/embedded-app-sdk` (`@sideroom/embedded-app-sdk`): `new SideRoomSDK(applicationId)`, `await sdk.ready()` (handshake, resolves `{application_id, instance_id, channel_id, guild_id}`), `commands.authorize({scope})` (the client asks the person, then calls `POST /oauth2/authorize` with `redirect_uri = <origin>/` and returns `{code}`; scopes limited to `identify` and `guilds`), `commands.authenticate({access_token})` (checked with `GET /oauth2/@me`, no cookie; a token of another application is refused), `getChannel`, `getInstanceConnectedParticipants`, `openExternalLink({url})` (http(s) only, after a confirmation), `commands.setActivity({activity})` and `subscribe(event, listener, {channel_id}?)` for `ACTIVITY_INSTANCE_PARTICIPANTS_UPDATE`, `VOICE_STATE_UPDATE` (Discord's shape: `voice_state`, `user`, `nick`, `volume`, `mute`, `pan`) and `SPEAKING_START` / `SPEAKING_STOP` (`{channel_id, user_id}`). Voice events are forwarded from the client's voice store for the instance's own channel only; a `channel_id` of another channel is refused. `setActivity` writes the person's presence activity (type Playing, this application, `details`, `state`, `timestamps`, `party.id`, `assets`) through the gateway presence update (op 3), with image names resolved through the application's Rich Presence assets (D-237; a name nobody uploaded is dropped), at most 5 calls per 20 seconds per frame (`RATE_LIMITED`); `null` clears it, and the host clears it when the frame unmounts or the instance ends. The protocol is documented at the top of `packages/embedded-app-sdk/src/protocol.ts`; neither side trusts a message from another window or origin. Not built: `getUser`/`getRelationships`-style commands.
* **Client (DEV-ACT-004, J-15).** The voice call bar and the composer's "+" menu ("Start an Activity", guild text channels) show the launcher only when the server answers `enabled`. The channel view that owns the instance shows a bar (Join / Leave / End for everyone) and reserves a slot; `ActivityDock` in the Lounge shell renders the one sandboxed iframe (`sandbox="allow-scripts allow-same-origin allow-forms allow-popups"`, `allow="fullscreen"`, `referrerpolicy="no-referrer"`) on `https://<application-id>.activities.<host>/`, laid full size over that slot, or docked as a small draggable window with "Return" and "Leave" when you are elsewhere in the Lounge. It is the same element in both modes, so the Activity keeps running while you navigate. Leaving the Lounge for another part of the app unmounts it.
