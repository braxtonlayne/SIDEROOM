# 15 — Threat model

XC-SEC-007, rewritten for RDY-SEC-004. A working document: what we protect, from whom, what stops them, and what is still open. It describes the system as built through wave 65 (the tree this document is committed with; reviewed against the feature phase, waves 27 to 39, for OPS-DOC-001, extended for each later wave through T60, and brought up to the security audit waves 60 to 65, D-609 to D-658, in T61 to T67 and in the rows they extend) and names, for every control, the file that enforces it and the test that proves it, so a reviewer can check the claim. When a control changes, change it here in the same PR.

**How the references were checked.** Every file and test named in backticks below was found by grep in the tree, not recalled. `scripts/threat-model.test.mjs` reads this document, checks that each named file exists and that each `file::name` pair finds `name` in that file, and fails any residual cell that says "open" without naming an `RDY-` item. It runs with the other automation scripts in `repo-checks.yml`.

## 1. Assets

| Asset | Why it matters |
|---|---|
| Account credentials (passwords, TOTP secrets, passkeys, recovery codes, session tokens) | Takeover of a member or of staff |
| Invitations and the account cap | The whole access model is "invitation only"; leaking or forging invites defeats it |
| Message content and attachments, including DMs | Private community |
| The Person graph (one Person per human, linked accounts, the invite tree, Discord identity links, sign-in addresses of the last 180 days) | It is the ban-evasion record; leaking it exposes who invited whom and who shares a network; abusing it targets people |
| The moderation register (reports, cases, evidence snapshots, holds, bans and appeals, the takedown register and counter-notices) | Contains reporters' identities, private DM snapshots, legal notices and the strike history of uploaders |
| Data-subject exports and the data-request queue | A package is a person's whole data; a request carries a verified identity and a legal deadline |
| The suspicion signals (inviter suspicion levels, evasion signals) | Heuristic accusations about people; wrongly exposed or wrongly acted on they do harm |
| Staff powers and the staff access log | Staff see and act across the platform; the log must be tamper-evident |
| Payment records, watch-only wallet descriptors and perks | Money, and the link between payments and accounts |
| Bot tokens, OAuth2 client secrets and tokens, interaction signing seeds, webhook tokens | Act as an application or as a member |
| Activity bundles | Third-party code that runs in members' browsers |
| Guest links and guest tokens (wave 43), crash reports (wave 45) | A guest link lets a person with no account into one game session; a crash report is client-supplied data that can carry whatever the page held |
| Web Push subscriptions (endpoint and keys) and the VAPID key | Reach a member's devices; a member-chosen endpoint is a fetch target |
| E2EE material (voice and video, bot identities) | Keys never reach the server |
| Operator secrets (`server.secret_key`, database, storage and SMTP credentials) | Root of trust for stored TOTP secrets and all data |

## 2. Actors

Anonymous visitor; invited-but-not-yet-member; member; malicious member (spam, harassment, attempts to read what they may not); staff member acting in good faith; compromised or malicious staff account; another site's page driving a visitor's browser; network attacker; compromised operator host; a bot token holder; a **developer** whose application, Activity bundle or webhook calls the platform; a **takedown notifier** (a rights holder or their agent: staff record their notice and counter-notice, they hold no account and use no form); a **data subject** (a person asking for access, rectification, restriction or erasure, through the self-service export or a staff-recorded request); a **banned person** appealing from outside a session; a **hostile Activity** (a third-party web app inside a member's browser).

## 3. Trust boundaries

Browser to Caddy (TLS) to `sr-server` (loopback or compose network) to Postgres and object storage. The browser also talks to the object store directly for presigned uploads and downloads. Activities run on a separate origin and are never trusted. Outbound: the server fetches only through the two SSRF-safe fetchers (T8), to the push service, the Esplora chain source, link targets, mapped Activity servers and lookup providers. Voice media goes browser to SFU, end-to-end encrypted (T16). The gateway and REST limiters, the staff access log chain and the secret key are per process or per host: this is a one-node design (T1, T17).

## 5. Out of scope

A compromised operator host (root can read everything on it); a member sharing their own screen or content elsewhere; endpoint malware on a member's device; legal process against the operator.
