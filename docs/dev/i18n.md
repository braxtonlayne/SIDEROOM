# Internationalisation: how a locale is added

English is the source language and the only shipped catalog. This page is the checklist for adding a second
one, and for checking that the app is ready for it. Extraction rules (what goes into the catalog, key format,
ICU) are in [i18n-extraction.md](i18n-extraction.md); this page is about everything around them.

## Where things live

| Thing                                           | Path                                                                                                                      |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| English fragments (the source)                  | `apps/web/src/i18n/messages/en/<fragment>.ts`                                                                             |
| Merge and duplicate-key check                   | `apps/web/src/i18n/messages/merge.ts`, `store.ts`                                                                         |
| First-paint catalog (entrance, a11y, pwa)       | `apps/web/src/i18n/messages/en.ts`                                                                                        |
| The rest of the English catalog (its own chunk) | `apps/web/src/i18n/messages/en.rest.ts`                                                                                   |
| Locale registry, `t()`, formatting helpers      | `apps/web/src/i18n/runtime.ts`                                                                                            |
| React hooks (`useT`, `useLocale`)               | `apps/web/src/i18n/react.ts`                                                                                              |
| Which paths paint before the full catalog       | `apps/web/src/i18n/corePaths.ts`                                                                                          |
| Language picker, account sync                   | `apps/web/src/settings/user/sections/App.tsx`, `apps/web/src/i18n/accountLocale.ts`                                       |
| Pseudo-locale generator                         | `scripts/pseudo-locale.mjs`, `apps/web/vite/pseudoLocale.ts`                                                              |
| Checks                                          | `scripts/i18n-audit.mjs`, `scripts/i18n-verify-diff.mjs`, `apps/web/src/i18n/*.test.ts*`, `e2e/tests/i18n-pseudo.spec.ts` |

## The catalog is a folder of fragments

`messages/en/` holds one file per area or owner: `export default { 'area.component.thing': 'English text' }
satisfies Record<string, string>;`. `en.ts` and `en.rest.ts` read the folder with `import.meta.glob` and call
`registerFragments`, which runs `mergeFragments`: the same key in two fragments throws at load, naming the key
and both files. Adding a fragment needs no other edit. A new feature adds its own fragment
(`p26-<name>-<n>.ts`); it never edits another one.

Only `entrance.ts`, `a11y.ts` and `pwa.ts` are bundled with the app. Everything else loads as the separate
`en.rest` chunk in parallel with the first paint, and every non-entrance route waits behind `CatalogGate`, so a
key never shows on screen.

### `corePaths.ts`

`isCorePath(pathname)` lists the routes that render from the three core fragments alone (login, register,
forgot, invite and reset links, and so on). Those routes skip the gate. A path that is not listed is safe: it
simply waits for the full catalog. Add a path there only if every key it uses is in `entrance.ts`, `a11y.ts` or
`pwa.ts`; `corePaths.test.ts` and `firstpaint.test.tsx` enforce it for the entrance routes.

## Adding a locale

Say the code is `de`.

1. **Write the catalog.** Create `apps/web/src/i18n/messages/de.ts` exporting a `Catalog`
   (`Readonly<Partial<Record<MessageKey, string>>>`). A missing key falls back to English, so a partial
   translation is allowed and visible as English text. Keep the ICU structure of the English string
   (arguments, `plural` and `select` cases, `#`); translate the literal text and add the plural categories the
   language needs (`one`, `few`, `many`, `other`). Quote a literal brace as `'{'`.
2. **Register it.** In `runtime.ts` add the entry to `LOCALES` (`{ code: 'de', label: 'Deutsch', dir: 'ltr' }`,
   the label is the endonym, `dir: 'rtl'` for Arabic and Hebrew) and a lazy loader to `LOADERS`:
   `'de': () => import('./messages/de').then((m) => m.de)`. Only the active locale is fetched.
   `negotiateLocale` then picks it from `navigator.languages` when nothing is saved; the picker in
   User Settings > Language lists everything in `LOCALES` that is not a pseudo-locale.
3. **Check the catalog.** `cd apps/web && pnpm exec vitest run src/i18n` (the English catalog test parses every
   message as ICU; add `de` to a catalog test of your own for the same on the new file) and
   `node scripts/i18n-verify-diff.mjs` (lists English text that was removed or changed without a matching catalog
   entry; the target is `MISSING 0`).
4. **Check the layout.** Run the pseudo-locale pass below. German and Finnish are the usual overflow cases;
   Arabic and Hebrew need `dir: 'rtl'` and the logical CSS properties the repo test already enforces.
5. **Backend copy.** Mail, push text and system messages follow the account locale
   (`PATCH /users/@me {locale}`, written by `chooseLanguage`). The server only honours tags it has catalogues
   for, so a new locale also needs its server-side templates; until they exist the account keeps English mail
   and the interface still switches.

Nothing else in the app names a language. Components call `t('key')` or `useT()`; none reads the locale.

## Dates, numbers and the clock

Screens never call `toLocaleString`, `toLocaleDateString`, `toLocaleTimeString` or `new Intl.*`. They use the
helpers exported from `i18n` (`runtime.ts`): `formatNumber`, `formatDate`, `formatTime`, `formatDateTime` and
`formatRelative`. All of them build their `Intl` formatter from one tag:

- the region override (`setFormatLocale`, set from User Settings > Language "Language and region"), if any;
- otherwise the UI locale (the pseudo-locales map to `en` and `ar`).

The 12 or 24 hour preference (`setHour12`, fed by the time format setting through `settings/user/prefs.ts`) is
applied to `formatTime` and `formatDateTime` and to `{t, time}` arguments in messages. Dates and numbers inside
a message use ICU arguments (`{d, date, medium}`, `{n, number, percent}`). Counts in sentences are ICU plurals,
never `n === 1 ? '' : 's'`.

## Pseudo-locales and the layout check

Two pseudo-locales exist for testing; they are never real languages and never reach the account.

- `en-XA`: accented letters, about 35 percent longer, wrapped in `[ ]`. It is generated at build time from the
  English fragments by `scripts/pseudo-locale.mjs` (`node scripts/pseudo-locale.mjs --out en-xa.json` prints
  the catalog) and served to the app as the virtual module `virtual:sr-pseudo-locale` by
  `apps/web/vite/pseudoLocale.ts`. A string that shows no accents is not going through the catalog; a string
  that loses its `]` is being cut off.
- `ar-XB`: the same text, right to left (`dir="rtl"`), for mirroring checks. It uses the runtime transform in
  `i18n/pseudo.ts`.

They are available:

- on the Vite dev server, always;
- in `vite preview` when the build was made with `SR_PSEUDO_LOCALE=1`
  (`SR_PSEUDO_LOCALE=1 pnpm --filter @sideroom/web build`, then preview);
- never in a production bundle: `import.meta.env.DEV` is false there and the flag is not set, so the code, the
  alphabet and the catalog are dropped. `scripts/check-bundle-budget.mjs` fails the build when any chunk holds
  them (it skips that check for a build made with `SR_PSEUDO_LOCALE=1`).

Add `?lang=en-XA` (or `ar-XB`) to any URL to preview it for that page load. Nothing is saved, so the next
plain load is English again. The Language picker shows the pseudo-locales on dev builds and in app test mode.

`i18n/pseudoLocale.test.ts` proves the generated catalog and the runtime transform produce the same text nodes
for every key, so the two cannot drift.

### The Playwright pass

`e2e/tests/i18n-pseudo.spec.ts` renders the entrance, a Lounge channel, Settings, Library home, a Cinema title
and the Admin home in `en-XA` at 1280 and 375 pixels wide, on Chromium, and fails when

- the page scrolls sideways, or
- text is cut off inside a control: an element that is, or sits inside, a button, link, tab, menu item, chip or
  badge clips its overflow (`overflow-x: hidden|clip`), is not an ellipsis truncation, and has
  `scrollWidth > clientWidth`.

Findings that belong to a screen outside the task that found them are listed in the spec's `KNOWN` array with the
file that has to change; a `KNOWN` entry that no longer matches fails the spec, so the list stays honest. To run
it: start `sr-server` and the Vite dev server as for any e2e run (`just e2e`, or the steps in
`docs/dev/handoff/feat-p18-integration.md`), then
`pnpm --filter @sideroom/e2e exec playwright test i18n-pseudo --project=chromium`.

## The two audits

- `node scripts/i18n-audit.mjs apps/web/src [--ts] [--json out.json]` counts probable un-extracted strings
  (JSX text, `aria-label`, `title`, `placeholder`, `alt`, `label`, `description`, `helpText`). The target is
  `TOTAL 0`. It ignores text that is code, not prose: comparisons and generics that merely look like JSX text,
  `sr-cli` commands, URLs and invite examples, and a short list of fixed technical names (`TECHNICAL_TOKENS` in
  the script). A new technical literal goes on that list, a new sentence goes in the catalog.
- `node scripts/i18n-verify-diff.mjs` compares the text a diff removes with the catalog. The target is
  `MISSING 0`.
