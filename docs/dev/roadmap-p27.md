### Rules every wave follows

The rules of [roadmap-p20.md](roadmap-p20.md) section 2 and [roadmap-p25.md](roadmap-p25.md) section 2 apply unchanged: worktrees `C:\Users\braxt\Desktop\SIDEROOM_wt\p<wave>-<agent>` on `feat/p<wave>-<agent>` with their own `CARGO_TARGET_DIR` `p<wave>-<agent>-target`, scratch database `sr_p<wave>_<agent>` and ports; at most three cargo builds at once on the machine and one cargo command at a time per agent, each `-j 2` (with four agents, the fourth waits on a build; the Split tables name a "no server" agent per wave where possible); ten migration numbers per agent, unused numbers stay unused, never edit a merged migration; the append-only shared files; generated files regenerated by the integrator; one i18n fragment per agent (`p<wave>-<agent>-<n>.ts`); a handoff with "Resume here"; integration on `integration/phase<wave>` with the full gate list; nothing pushed, merged or downloaded without the owner; proof over claims; standard `ubuntu-latest` runners only, no new marketplace action. Additions for this phase:

- **Downloads only from section 17.** A dependency not in the downloads table is not added. Each one is downloaded by the owner or the commander before the wave that needs it, on the integration branch or the agent's worktree; no agent downloads anything. Every version is at least two weeks old at download time; the owner pins the newest such release and the handoff corrects the table's version if it differs. GPL is acceptable (D-309); a non-commercial licence is refused because the instance sells Patron tiers (note 6). Each new licence text goes into `THIRD_PARTY_NOTICES.md`, `deny.toml` or `scripts/check-licenses.mjs` by name, and `cargo deny check` and the web licence step prove it.
- **The IMMUTABLE RULE.** End-to-end encryption of calls, per-route authorization and the tamper-evident audit and access logs are not features, settings or flags. No feature id or setting key may gate them, no config field may turn them off (the one that does, `voice.e2ee`, is removed in wave 28, OPS-IMM-001), and the harness `crates/sr-server/tests/immutable_rules.rs` (wave 28) runs on every wave: with every registered feature killed at platform scope and every setting at each end of its range, staff reads still write the access log, admin actions still write the audit log and the chain verifies, the refusal phase of the authorization matrix still refuses, and a voice sender that has not completed the E2EE join is not forwarded. An agent that adds a flag adds its id to the harness's catalog walk (automatic through the registry) and may not add a name that matches the deny pattern (`e2ee`, `encrypt`, `audit`, `access_log`, `authz`, `authorization`, `permission`), which the harness pins.
- **Every new route** goes into `crates/sr-api/tests/route_matrix.tsv` with an explicit AUTHZ class and into `crates/sr-server/tests/authz_matrix.rs` with a read phase (every actor) and a write phase (the rightful actor admitted; `WRITE_OBSERVED` may only shrink). New AUTHZ classes (`storage_scope`, `mount_owner`, `bridge_admin`, `node_pair`) get their actors in the cast; the cross-tenant sweep covers every new `{…_id}` segment. OpenAPI, the api-client and the MSW mocks regenerate.
- **Tokens only.** Every new component (player skins, the drawer and its gadgets, the shelves, the activities, the banner) styles itself with the semantic custom properties of `packages/ui` and layout slots; no raw colours, no raw fonts, no per-skin CSS files that bypass the theme. `scripts/check-css-tokens.mjs` (wave 27, byos-ui) fails on a hex or named colour or a `px` font size in any CSS file under the new directories, and the Lounge theme stays the default.
- **Heavy compute in WASM, in Rust.** Remux, search, tag reading, GIF encoding and the emulator cores run in the browser; new WASM crates live in `crates/*-wasm` and are built by `packages/wasm` (wasm-pack is already installed by `wasm.yml`). The exception is ffmpeg.wasm (not ours, C compiled by its authors) and the emulator cores (likewise).
- **BYOS: credentials.** A mount's secret key is sealed with `sr_db::sealed` (AES-GCM under `server.secret_key`, AAD = the mount id), column `secret_key_enc`, so `secret_columns.rs` accepts it; `sr-cli rotate-secret-key` re-seals mounts like TOTP secrets and signing seeds, with a Postgres test; no route ever returns the secret (the view carries the access key id and the last four characters of the secret as `key_hint`); the connection test never echoes it; logs and the access log carry the mount id only. The connect screen shows a bucket-scoped policy for each provider and the test warns when a key can list other buckets (note 2).
- **BYOS: scopes.** One function decides every read: `sr_storage::scopes::resolve(viewer, mount, key) -> Scope | Refused`, used by every listing and presign route, fail closed (a non-member, a non-friend, a friend without the kind's share, a role without the grant, a delisted key, a disabled mount, a mount whose owner is suspended: all refused). A staff read of a mount that is not theirs goes through the access log (`staff_access_log` kind `storage.read`), never silently.
- **BYOS: CORS.** No mount serves a browser read until the checker has passed once (`cors_ok_at`), re-checked daily by a job and after any read failure the client reports; the rule is the one-origin-per-rule shape of `s3admin::cors_xml` (D-175), extended to `GET`, `HEAD` and `PUT`, allowed header `content-type` (lowercase, the wave-24 lesson), exposed headers `etag`, `content-range`, `accept-ranges`, `content-length`; origins are `server.public_url` only, never a wildcard. "Apply CORS" is one click through `S3Admin::put_bucket_cors` and `sr-cli storage ensure-cors --mount <id>`; providers that refuse the API get the provider's manual steps on screen (note 3).
- **BYOS: presign TTL.** A `GET` presign lasts `byos.presign_ttl_secs` (default 900) and never more than `byos.presign_ttl_cap_secs` (default 3600, hard ceiling 86400 enforced in code, so `MAX_PRESIGN_SECS` of 7 days applies only to multipart part `PUT`s, which keep 3600); never longer than the caller's session has left; presigned URLs are never stored, logged, sent on the gateway or put in a message; the client drops a URL at its `ex`. HLS playlists rendered over a mount carry `#EXT-X-SR-EXPIRES`, and the player refreshes the playlist five minutes before it (one hls.js loader hook, no replay of expired URLs).
- **BYOS: zero proxy, with three named exceptions.** The server never streams a mount's bytes to a browser. It reads a mount's bytes itself only for: the catalog's header read (the first 1 MiB of a file, for tags and probes), the scrapbook archive copy (one object, size-capped), and thumbnails of images under 20 MiB. Each exception is a listed function with a size cap and a test; `grep` for `get_stream` outside those three in the mount code is a repo check.
- **BYOS: keys.** Every object is addressed as `(mount_id, key)`; a key from user input passes `sr_storage::path::safe_key` (no `..`, no leading `/`, NFC, at most 1024 bytes, no control characters) before it reaches a presign or an S3 call; a test pins each refusal.
- **Beta usability (note 10).** From wave 29 on, every wave's integration runs the full Playwright suite plus the BYOS-over-Garage job before the owner's beta guild is upgraded; a wave that breaks a beta flow is fixed before the next one starts, and the checkpoint after wave 34 may reorder 35 to 38.

## 3. Cross-cutting design decisions (so the waves agree)

**Permission bits.** The spec names five role permissions (`VIEW_GUILD_CINEMA`, `VIEW_GUILD_LIBRARY`, `VIEW_GUILD_MUSIC`, `UPLOAD_TO_GUILD_STORAGE`, `MANAGE_GUILD_STORAGE`). The permission word is an `i64` with bits 61 and 62 free and 63 unusable; 47 and 53 to 55 are Discord's and may be assigned by Discord later. Five bits do not fit, and a second permission word touches roles, overwrites, `sr-permissions-wasm`, the role editor and the matrix: a wave by itself. The plan therefore keeps the five names as **storage grants**, rows of `guild_storage_grants(guild_id, role_id, grant)` evaluated by `sr_storage::scopes::guild_grants(guild, member, roles)` with owner and `ADMINISTRATOR` bypass and `MANAGE_GUILD` implying `manage` (the shape of an emoji's `role_ids`, D-376 (b) style, no channel overwrites because a shelf belongs to no channel). The role editor shows them as five toggles in a "Storage" group under the SIDE ROOM section, the role payload carries `sr_storage_grants`, and doc 07 section 2 documents them as grants, not bits. Bits 61 and 62 stay free for a future capability that needs channel overwrites. The owner may instead spend 61 and 62 (`VIEW_GUILD_SHELVES` as one bit for the three kinds, `MANAGE_GUILD_STORAGE`, with upload as a grant); that is decision O-1 of section 18 and the default is the grants table.

**The instance bucket (note 5).** On the first start after wave 27, `storage.*` config seeds mount 1 (`owner_kind = platform`, label "Instance", credentials sealed from the config) if `storage_mounts` is empty; the config stays the bootstrap source and its keys are still what the server itself uses for attachments, emoji, avatars and transcoder output. Cinema, Library and chat read media through `MountResolver` (wave 27, byos-instance) and existing rows resolve to mount 1 with their current keys, so nothing moves. The beta guild is attached to mount 1 as a Guild Shelf by the owner in Admin (one click, `POST /admin/storage/mounts/1/attach`). There is one read path from wave 27 on; the `/cdn/{*path}` proxy stays for the server-owned prefixes (attachments, emoji, avatars, sprites) and for mount 1 where CORS cannot be set (the memory backend of tests), and a repo check lists which routes still proxy.

**Zero-proxy and the access log.** Members reading their own or shared shelves are ordinary use and are not logged (doc 07 section 5 logs staff reads of private content). Staff reads of any mount that is not theirs are logged. A presign is "the access"; the bucket's own logs are the owner's.

**E2EE is the only voice mode (OPS-IMM-001).** `voice.e2ee` leaves the config (`e2ee = false` becomes a config error), `VITE_SR_VOICE_E2EE` and `apps/web/src/voice/e2ee/flag.ts` go, `playwright.e2ee.config.ts` folds into the main config, and `sr-voice` forwards a sender's media only after the room has seen that sender's op 101 key package (D-249), so a client or bot built without E2EE joins but is never heard. The bot SDK's `voice-e2ee` feature stays optional for `--no-default-features` builds but such a bot cannot send.

**Music in voice (WG2).** The server never decodes or encodes audio (D-201): the browser encodes the music track with its own Opus encoder as a second audio sender (`stereo=1; sprop-stereo=1; maxaveragebitrate=320000; useinbandfec=1; usedtx=0` in the SDP, `tuneOpus` extended) under the same per-sender frame encryptor (D-249, codec-aware clear ranges already cover Opus), the SFU forwards one more audio mid per member, and the governor counts it. 24/7 listening rooms are a server-side playlist cursor (a job advancing `position_ms` and publishing `LISTENING_ROOM_UPDATE`); audio reaches listeners by synced local playback (each listener presigns from a mount it may read). A room in SFU mode needs a present DJ; the UI says so.

**Mount-indexed media and the review pipeline.** Media found in a mount bypasses submissions and review: the mount owner is responsible, moderation is takedown and delisting (BYOS-LEG-001). Catalog rows from mounts carry `source = 'mount'` and `mount_object_id` on the existing `cinema_titles`, `library_series`/chapters and the new `music_tracks`, so Discover, Browse, the reader and the player need one visibility filter (`scopes::resolve`), not a second catalog. Pages of a CBZ are read in the browser by range requests (two for the central directory, one per page, `sr-library-wasm` plus the `zip` crate already in the lock); EPUB and PDF go to the existing foliate-js and pdf.js readers from a presigned fetch; no page is ever converted into the instance bucket.
