## Done

### SEC-AUD-150: a `/cdn/mount` link always tells the bucket what to answer (D-637)
- `S3Multipart::presign_get_as(key, ttl, content_type, disposition)` and `presign_get_as_at(.., unix_secs)` (`sr-storage/src/s3multipart.rs`): a SigV4 query-string GET with `response-content-type` and `response-content-disposition` in the signed query; `ttl` clamped like `presign_part_at`; `check_key` first; control characters in an override are refused.
- Trait: `ObjectStorage::presign_get_as(key, ttl, &ResponseAs { content_type, disposition })`, default `StorageError::PresignUnsupported` (`storage.rs`; `ResponseAs` re-exported from the crate root). No other implementation of the trait needed an edit (they take the default).
  - `ObjectStoreStorage` holds an optional `S3Multipart`, set once when the client is built: `Mount::storage` attaches the mount's own (`Mount::multipart`: endpoint, bucket, region, path style, opened secret), `ObjectStoreStorage::s3` (the instance bucket) builds one from its settings (path style, as that constructor already is). The in-memory backend answers a fake `memory://` URL that carries both values as query parameters (`in_memory_without_overrides()` is a test constructor for a store that cannot sign them).
  - `PrefixedStorage` forwards the new method with the mount prefix applied exactly as `presign` does. It was the only forwarding wrapper in `sr-storage` (`impl ObjectStorage for` grep: `ObjectStoreStorage`, `PrefixedStorage`; the others are test doubles in other crates and take the default).
- `cdn/mount.rs`: the response is decided from the key's file name with `content::from_hls_extension` (which falls back to `from_extension`): an inline media type is forced as itself with `inline`; everything else is `application/octet-stream` with `attachment` and the file name through `content::disposition`. Then `presign_get_as`. `PresignUnsupported` and every other error answer 502 "storage unavailable" with a warn naming the mount and the error, never the URL. Takedown check, TTL clamp and response headers unchanged. The signing step is `presigned_redirect(&dyn ObjectStorage, ..)` so a test can hand it a storage that cannot sign overrides. `content::DOWNLOAD` became `pub(super)`.
- The instance bucket (mount 1) is still refused by `/cdn/mount` (400, unchanged), so the instance `s3()` override signer is built and tested only through the trait; nothing calls it yet.

What `from_extension` / `from_hls_extension` know (read before relying on it): png, jpg/jpeg, gif, webp, avif; mp4/m4v, webm, mov, m4s; vtt; mp3, ogg/oga/opus, flac, wav, m4a, aac; and, for HLS: m3u8, ass, ttf, otf, ttc, woff, woff2. Everything the app shows inline from a mount through `<img>`, `<video>`, `<audio>` or an HLS player is on that list. Extensions NOT known, so now forced to a download: `.svg` (deliberately), `.mkv`, `.avi`, `.ts`, `.mpd`, `.m4b`, `.wma`, `.jfif`, `.bmp`, `.ico`, `.heic`, `.srt`, `.pdf`, `.epub`, `.cbz`/`.cbr`, `.json`. Readers that `fetch` (EPUB, PDF, comics archives) ignore the header and are unaffected. I did not find a `<img>`/`<video>`/`<audio>`/`<iframe>` load of a mount object through `/cdn/mount` by an unlisted extension, but I did not check every consumer of mount URLs: owner/planner question below about `.mkv`, `.bmp`, `.srt` (inert media or text that a player might fetch; I added none to the table).

## Proposed threat-model text (the row wave 61 added for D-629, "Stored active content on the bucket origin")
Mitigation: the app stores active types as `application/octet-stream` (browser-direct uploads, D-629) and a `/cdn/mount` link forces the response type through the signed URL (`response-content-type`, `response-content-disposition`, D-637): inline media by extension, everything else a download. Residual: objects stored before D-629 and objects put into the bucket outside the app keep their type for the bucket's own URL and for the other presigned GET routes (SEC-AUD-151: storage browser, shelf object URL, tracks, jukebox, scrapbook); closed for `/cdn/mount` links only. New residual: a provider that ignores `response-content-type` / `response-content-disposition` on a presigned GET serves the stored type again. The mount form offers S3, R2, B2, MinIO, Wasabi and Garage (`Provider` in `mounts.rs`). Amazon S3 documents both parameters for signed GETs. MinIO and Garage implement the S3 GetObject response-override parameters in their own docs as far as I know, but I did not verify any of the six against its documentation or a live bucket (no network, and the brief said not to guess), so the row should say "unverified for R2, B2, Wasabi, MinIO, Garage" until the connection test checks it (suggestion: the mount's connection test presigns a GET of a small probe object with an override and reads the response header).
