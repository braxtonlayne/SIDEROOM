# Handoff: feat/p8-watch-parties (Watch Parties, full stack)

Worktree `SIDEROOM_wt/p8-watch-parties`, branch `feat/p8-watch-parties` (base integration/phase7). New crate `crates/sr-watchparty`, migration `0480_watch_parties.sql`, `/watch-parties` routes in `sr-api`, wiring in `sr-server`, `apps/web/src/watchparty/`, and small edits in the Cinema, Lounge and store code listed under "Touched outside the feature". API and events are documented in `docs/specs/watch-parties.md` section 7 (as built) and `docs/05-api-and-gateway.md` section 6.3.

## Done
- **State machine** (`state.rs`, pure): position arithmetic from the server clock (`position + (now - at) * rate`), play, pause, seek (clamped), rate 0.5 to 2, buffering auto-pause and auto-resume, `ended` with a 2 s tolerance, live parties (no seek, pause or speed). Every change rebases at "now" and bumps `version` by one; a no-op leaves the version alone. Optimistic `expected_version` gives a 409 with the current playback.
- **Rules** (`rules.rs`, pure): who may control (host, named controllers, `CONTROL_WATCH_PARTY` in the bound channel, everyone), buffering aggregation (stall of 1.5 s pauses, resume when nobody stalls, continue without stragglers after `max_wait_ms`), host handover (controller first, then seniority), queue reordering, reaction and message validation, a sliding-window limiter.
- **Service** (`service.rs`, `playback.rs`, Postgres): create (private, channel, DM), join with invite code or channel access, leave, end, kick with a ban, host transfer, controllers, settings, heartbeat (liveness, RTT, buffering, ready), commands, change media, queue (add, move, remove, skip, auto-advance on `ended`), reactions, ephemeral chat, audit log, sweep (silent members after 90 s, empty parties after 5 minutes unless persistent, expired buffering waits, ended parties deleted after 24 h). Every mutation locks the party row (`FOR UPDATE`) so commands are applied in order. One account is in one party at a time.
- **Rules from the spec**: the title must be published and playable (the catalog's `resolve_play`, so each viewer still gets HLS only through the normal `GET /cinema/assets/{id}/playback` checks; the party never hands out media URLs); a restricted title needs the starter's age confirmation, joiners without it get 403 `900011`, switching to a restricted title removes unconfirmed participants, channel viewers without confirmation see a masked card (D-184); rate limits (commands 12 per 5 s, reactions 8 per 5 s, messages 6 per 10 s, buffering reports 12 per minute, creates 5 per minute); one live party per bound channel; concurrent parties per server limited.
- **Events**: `WATCH_PARTY_UPDATE`, `WATCH_PARTY_PLAYBACK`, `WATCH_PARTY_REACTION`, `WATCH_PARTY_MESSAGE` as user-scoped dispatches to the participants (`created`, `ended`, `media`, `host_changed` also reach the viewers of the bound channel). No gateway code changed.
- **Wiring** (`sr-server/src/watchparty.rs`): `CinemaPlayGate`, `ChatChannelAccess` (roles, overwrites, DMs), the `watchparty.sweep` job (id 172, every 10 s), the timer worker for buffering waits. `START_WATCH_PARTY` was added to the default `@everyone` permissions of new servers (one line in `sr-chat/src/perms.rs`; existing servers keep what they have).
- **Frontend** (`apps/web/src/watchparty/`): `sync.ts` (pure clock estimator, expected position, drift policy), `controller.ts` (outside React like the player session: server-authoritative, applies state with drift correction, reports buffering after 1.5 s, heartbeat every 15 s that also repairs lost events, commands guarded by `expected_version`, raised hands), `runtime.ts` (the Cinema `PlayerSession` as the `SyncPlayer`, HTTP API, gateway dispatch seam), the theatre (stage with the session's own `<video>`, control bar with host or controller controls and a disabled view with "Request control" for others, reactions overlay, "Waiting for X" banner, "Click to join the playback" when autoplay is refused, ready check), Chat / Queue / People tabs (speaking indicators from the voice store, host badge, buffering and ready marks, grant, make host, remove, drag and button reordering, add from search with an episode picker, party settings), invite dialog with copyable link, `StartPartyDialog` (title picker plus destination picker for private, channel or DM), a channel strip with a live party card, "Start/Join Watch Party" in the voice call controls, the Title page "Watch together" button, route `/cinema/party/$id?code=`.
- **Mini player**: leaving the theatre hands the picture to the existing mini player (always, paused or playing, while the party is followed); its "expand" returns to the party (`bridge.ts` got an `expandHref`); closing the mini player leaves the party. The controller holds the gateway open while a party is followed (`holdGateway` in `store/connect.ts`; the Lounge's `disconnectGateway` waits for the last hold).
- **Reduced motion**: reactions do not travel (CSS media query), they fade in a row. Keyboard: every control is a button or native input; the panels are `Tabs`; the dialogs are the UI kit `Modal`.

- **10-client drift simulation** (WP-FE-013): ten real controllers against one in-memory server with browser clocks up to 3 s off, media clocks up to 0.04 percent fast or slow, 10 to 100 ms latency per leg (asymmetric), staggered joins. Over 10 simulated minutes the worst deviation from the server position was under 300 ms and the worst gap between any two viewers 300 ms or less; a host seek is followed within 3 s, pause and resume together, a short stall (under 2 s) is corrected by rate nudging only, 6 s lost is one hard seek.

## What was only tested with fakes
No real stream was played anywhere. The web tests use a fake HLS engine and a mocked `HTMLMediaElement` (the player's own test doubles); the drift simulation uses a player clock that can run fast or slow. Real `<video>` stalls, real seek latency, autoplay policy in browsers, the native Safari path and the gateway over a real WebSocket were not exercised. Server side, the clock and the catalog are real only in the ignored Postgres tests; the events go to a recorder, not a socket. The browser pane and e2e ports were not used.

## Decisions
- **Drift ignore band is 100 ms, not 250 ms** (hysteresis: nudge until under 40 ms). With 250 ms the simulation left two viewers up to 440 ms apart; the acceptance criterion says 300 ms of each other.
- **No new channel type.** A party is bound to an existing text or voice channel or DM, or is private. "Watch Party channel" behaviour is a bound voice channel party with `persistent` (survives being empty, the first person to join takes the host seat). Adding a type touches `sr-chat`, the channel UI and the permission pipeline; owner decision.
- **Clock sync over HTTP, op 100 stays reserved.** `GET /watch-parties/time` and the heartbeat answer carry `server_time_ms`; every playback state carries it as well. Fewer moving parts than a gateway op and testable without a socket.
- **User-scoped dispatches** rather than new `DomainEvent` variants, so the gateway needed no change. Event fan-out is per participant (at most 100).
- **Raised hand = a reaction** with the hand emoji; the host sees "wants control" and a Grant button. No server concept of a control request.
- **Private party chat is ephemeral** (`POST /messages`, not stored). Channel-bound parties link to the channel's own chat; the theatre does not embed it.
- **Age rule on media change**: switching to a restricted title removes unconfirmed participants (with an `age_restricted` removal event) instead of refusing, so a host can always change the title.
- **Audit** has its own table (`watch_party_audit`); the guild audit log has fixed Discord action types. Playback commands are not audited (rate limited instead).
- **Pairing**: an account is in one party at a time; creating or joining another leaves the first (host role passes on).

## Not done
- **WP-BE-008** the live-updating system message in the channel's chat (the `ChatHook` port and `Announcement` exist, nothing implements them; there is no chat message type for it). The channel strip shows a live card through the gateway meanwhile.
- **WP-BE-009** a dedicated channel type. **WP-BE-010** Live TV parties: the `live` flag, the no-seek rules and the state machine are tested, but no Live TV catalog supplies a `PlayGate` yet (sr-tv is another agent's). Live TV "Watch together" and the message-card "Watch together" are not wired; `StartPartyDialog` takes a title or none, so Live TV can use it.
- **Concurrent party limits by server level**: a constant 2 (`FreeTier`) until server levels exist (`GuildLimits` port).
- **WP-FE-012** webcam bubbles. No e2e test. The theatre has no picture-in-picture or Chromecast of its own (the player session's element is reused as is). The party's media starts at the expected position but the Cinema player's own progress saving still runs for the viewer (their history records what they watched).
- The theatre does not show the party's `queue` on the mini player and offers no "request control" feedback beyond the hand.

## Known issues
- `cargo deny check` fails on advisories for the existing `rustls` dependencies (RUSTSEC-2026-0346 to 0349 at the time of writing); nothing in this branch changes that tree (only `getrandom`, already locked, was added to a crate).
- Chrome throttles timers of a hidden tab to once a minute after about five minutes; the heartbeat (15 s) then runs about every 60 s, inside the 90 s limit, but a longer throttle would drop the participant. The next visit rejoins.
- The Lounge channel view fetches `GET /channels/{id}/watch-party` once per opened text or voice channel (404 when none).
