## Done
- **Migration `1690_scrapbook.sql`** (range 1690-1699, only 1690 used): `scrapbook_targets` (the shelf and who delegated `upload`), `scrapbook_entries`, `scrapbook_objects`, `scrapbook_removals`.
- **Module `lounge.scrapbook`** (`crates/sr-features/src/modules/scrapbook.rs`): `default_enabled: false`, new trait hook `Feature::operator_gated`. A gated module is off in every server, absent from Guild Settings > Modules (`GET /guilds/{id}/sr/features` skips it, `PATCH` answers unknown feature) and refused by the scrapbook routes (404) until the platform scope holds an explicit `enabled: true`. The platform `true` only *offers* it: servers still switch it on themselves; the platform `false` is the kill switch as for every module. Settings: trigger emoji, threshold (default 5), roles allowed to send by hand (plus `MANAGE_MESSAGES`), ignored channels, age-restricted policy, and `max_object_mib` (platform scope only, 1 to 200, default 200). `client_visible: true`, so `GET /sr/features/flags` tells the web whether the operator offered it.
- **Reaction trigger**: the module counts distinct reactors (the author's own reaction counts) and leaves a `req:<message>` row in its runtime state; the job `scrapbook.requests` (singleton id 1690, every 30 s) performs it (re-checks that the module is still on, loads the message, archives, retries a passing failure five times with a backoff, drops a lasting one).
- **The one allowed server-side copy** (`crates/sr-storage/src/scrapbook.rs`, `copy_object`): one object from the instance bucket into the guild bucket under `scrapbook/<yyyy>/<mm>/<message_id>/<n>-<file>`, size checked up front and again while streaming against `scrapbook.max_object_mib`, one request below 8 MiB and a multipart upload (aborted on failure) above. Oversize files and files past ten per message are skipped and counted; the text is kept. A failed copy rolls back the copies already made. Archiving is idempotent per message.
- **Service account** (`PgScrapbookBuckets` in `crates/sr-server/src/scrapbook_jobs.rs`): writes only to the mount named in `scrapbook_targets`, and only if that mount is owned by *this* guild, is active, and the member who delegated it still holds `upload` on it (`scopes::may_upload`, checked on every copy). Never to a member's bucket, another server's, or the instance bucket. Every bucket call has a deadline (10 s, 120 s for data) so a dead third-party endpoint cannot hang a request for minutes.
- **Cascade on message delete, never silent.** `spawn_cascade_consumer` listens on the event tap for `MessageDeleted`, `MessagesBulkDeleted` and `ChannelDeleted` (every publisher, so moderation, takedown and feature-action deletes are covered, which a hook inside `ChatService` would not be) and runs `Archiver::cascade`. Entries and one `scrapbook_removals` row per copy change in **one statement**; then each copy is deleted from its bucket. A bucket that refuses leaves a `failed` removal with the error, the attempt count and the next try (1 min doubling to 6 h). The managers read the list at `GET /guilds/{id}/scrapbook/removals`, the module status counts them, the gallery's shelf panel lists them with "Try again now" and "I deleted it myself", and the member who removed an entry is told when a copy could not be removed yet. The job `scrapbook.removals` (singleton 1691, every 5 min) retries due removals and **reconciles** entries whose message is gone, deleted or hidden by staff without an event (lost tap, retention purge). The cascade runs whether or not the module is still switched on. Re-archiving a message cancels its own pending removal.
- **Routes** (`crates/sr-api/src/routes/guilds/scrapbook.rs`, 11 operations): status, gallery (filter by date, channel, tag, member; cursor paging; facets), send by hand, tags, remove, presign one copy, choose and drop the shelf, the removal list, retry, dismiss. An entry is listed only to members who hold `VIEW_CHANNEL` of its source channel (threads follow their parent); a file is signed only through the existing storage `presign` route, so the viewer's own storage scopes decide (a member without a view grant sees the text and "not shared with you"). Removing an entry works whatever the module's state. Bots are refused (`auth/policy.rs`).
- **DSR** (own file `crates/sr-db/src/scrapbook_legal.rs`, two registration lines): `scrapbook.json` in the export (entries about your messages with file names and sizes but never keys, entries you sent, shelves you allowed); erasure deletes the entries about the member and queues the copy removals in the deletion transaction, clears `archived_by`, and unlinks a shelf the member delegated (a manager must grant it again).
- **Web** (`apps/web/src/lounge/scrapbook/*`): masonry gallery at `/channels/:guild/scrapbook` (a static sibling route), filters, lazy per-file presign, tag editing, remove, manager panel (shelf picker, removal list), the "Send to Scrapbook" entry in the message menu, a sidebar row, and the channel banner ("a message with N reactions of X is kept in this server's Scrapbook"). Strings in `i18n/messages/en/p34-prf-scrapbook-1.ts`; tokens only (`check-css-tokens` clean), logical properties only. Nothing here is reachable from a public surface: `scripts/entrance-denylist.json` gained the word `scrapbook`; `build-web` + `check-entrance-isolation` report every surface ok.

## Decisions (conservative defaults, please confirm)
- **"The module's service account with the Guild Shelf `upload` grant"** is implemented as a delegated grant: a manager picks the shelf and must themselves hold `upload` on it; the grant ends when they lose it, when the shelf stops being the server's, is switched off or delisted. Roles carry grants, not accounts, so there is no new principal. Alternative: a real per-guild service account row in `guild_storage_grants` (needs a role-less member kind).
- **Who may send by hand**: the `roles` setting plus `MANAGE_MESSAGES`. The reaction path needs no role (the threshold is the gate). Empty `roles` default means managers only.
- **Entries are visible by source-channel `VIEW_CHANNEL`** at read time, not frozen at archive time, so closing a channel hides its entries at once.
- **No `sr-chat` change**: the roadmap's "message-delete hook (one call)" is the bus consumer plus the reconcile sweep (see above); adding a `MessageHooks` method would have missed deletes that do not go through `ChatService`.
- Reaction counting includes the author's own reaction (Starboard's `self_star` has no meaning for a vault).
- `scrapbook.max_object_mib` lives as a platform-scope field of the module, not an `sr-admin` setting.
- Age-restricted channels: skipped by the reaction trigger unless `nsfw = allow`; a manual send follows the sender's rights.
