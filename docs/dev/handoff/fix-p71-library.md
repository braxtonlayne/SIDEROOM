## Item 2, SEC-AUD-254 (a package upload that cannot be left unfinishable)

- **Confirmed by reading** `package_upload.rs` (base): `complete` listed parts and called the store's `complete` first, then updated the row; a failure between left `uploading` with the object assembled and the store without the upload, so every later `complete` died in `list_parts` ("The storage did not accept the uploaded parts. Start a new upload."); `discard` aborted parts only when the state was `uploading` and deleted the object only otherwise, so a stuck `uploading` row leaked the object; `sweep` expired a `checking` upload on `expires_at` which `complete` never moved.
- **Fix** (no new state, no migration): `complete` first asks the store (`storage.head`, as `attachments.rs:281` does) whether the object is there; if so it skips the parts; if the store's `complete` fails it asks again and carries on when the object is there (that is what the second of two concurrent calls sees). `discard` always aborts the open parts (an error is only logged: a store that no longer knows the upload answers with one) and deletes the object (not there is done), whatever the state; `abort` and `sweep` use it. A check that cannot be queued now also deletes its staged object (before: the row went `refused` and the zip stayed for ever). If the row moved under `complete` (given up or expired while the store assembled) the object is discarded.
- **Allowance I chose: 6 hours** (`CHECK_ALLOWANCE_HOURS`), `expires_at = GREATEST(expires_at, now() + 6 h)` in the same UPDATE that moves the row to `checking`. How long an ingest may take: `package_jobs.rs` has no time limit, 3 attempts (`INGEST_ATTEMPTS`, backoff 5 s then 10 s) and the checker's read budget is four times the object plus 16 MiB (`zipstore.rs`); at a few MB/s on the largest tier (4 GiB reviewed) that is about an hour per attempt, so 6 hours covers three. A check still not done after that is stuck and the sweep ends it (tested).
- **Tests** (new file `crates/sr-activities/tests/package_upload_db.rs`, Postgres; a part store wrapper behaves like S3: a completed upload is gone, completing is serialised; the failed row update is made by a trigger, so no switch was added to the code): (a) `complete_can_be_asked_again_after_the_row_failed_to_move`; (b) `giving_an_upload_up_leaves_nothing_in_the_store_in_every_state` (uploading with the object assembled, uploading with parts only, checking; and a second abort); (c) `a_check_queued_late_is_not_expired_under_it` (an upload with 10 minutes left has about 6 hours after `complete`; one with 20 hours is not shortened; a stuck check past its time is still expired and its object freed) and `the_sweep_frees_the_object_of_an_upload_the_row_never_moved_on`; (d) `two_complete_calls_at_once_both_succeed_and_queue_one_check`; plus `a_check_that_cannot_be_queued_frees_the_staged_object` and `complete_with_a_part_missing_is_still_refused_and_the_upload_stays_open`. "Asked again after success answers the current state" is in (a) and in the existing `complete_queues_the_check_and_the_status_ends_ready_with_the_bundle` of `sr-api` (unchanged, CI runs it).
- **Docs**: `docs/05-api-and-gateway.md` (the package upload row) and `docs/specs/developer-platform.md` (the resumable upload paragraph). "Start a new upload" appears in no doc or web string except the server message.

## Item 3, SEC-AUD-255 (`sr-cli bootstrap` cannot be left half done)

- **Confirmed by reading** `commands.rs` and `accounts.rs` (base): the system user and the Owner were two committed transactions, then `create_staff_guild` (itself a series of separate statements after `insert_guild`'s transaction: staff channels, `#alerts` in `settings`, roles, appointment) and the login link. `has_real_accounts` was the only guard, so after the Owner was committed every later run said "already bootstrapped". **What an operator could do in that state: nothing in `sr-cli`.** `login_link` was reachable only from `bootstrap`; `sr-cli staff ...` (appoint, revoke) needs a Staff Server ("no Staff Server yet; run `sr-cli bootstrap` first", `commands.rs:694`); the server's start-up repair of staff channels (`ensure_channels`) repairs channels of a Staff Server that exists and does not make one. I found no other command that makes a Staff Server or a login link for the Owner. The way out was hand-written SQL.
- **Fix taken: (b).** A new `accounts::try_bootstrap_lock` (a `pg_try_advisory_xact_lock` held by an open transaction: released when the command ends, however it ends; a second bootstrap is refused with "another bootstrap is running"), `accounts::real_accounts`, and in `sr-cli`: `bootstrap_with` under the lock. State rules: no real account: as before (system user, Owner, Staff Server, link). Exactly one real account whose Staff Server is missing or unfinished (no staff-server row, or no appointment row for that account; a revoked appointment still counts as done): it is finished only if that account is `active`, its username and email are the ones given and **the password given verifies against its stored hash**; then `finish_staff_guild` (new, in `guilds.rs`; `create_staff_guild` now ends with it) makes whatever is missing (staff channels by name, `#alerts` in `settings`, roles, appointment; each step only where missing) and a new one-time login link is printed. Anything else with accounts is refused as before. The password rule (length, strength) is checked before anything is written (a test shows a weak password leaves no row at all, not even the system user).
- **Why this opens no new door:** a finished installation always has a Staff Server and the Owner's appointment, so it is refused exactly as before, with any credentials. The half-made state is entered only by a run that stopped, and the finishing run proves it is the same operator: same username, same email and the Owner's password (a stranger, or an operator with another password, is refused and nothing is written, no token either; tested). Before, a finished or half-made installation could not be given a link by `sr-cli` at all; now only the one who knows the Owner's password can, and only while the install is unfinished. Someone with that password can sign in anyway.
- **Tests** (in `commands.rs`, Postgres): `a_stopped_bootstrap_is_finished_by_the_next_run` (a trigger makes the Staff Server's insert fail after the Owner is committed; a run with the trigger still there fails the same way and makes nothing twice; after the trigger is dropped the next run finishes, prints a link of the public URL; the run after that is refused and no second guild exists); `a_half_made_staff_server_is_finished_not_duplicated` (appointment and `#alerts` removed from a finished install: one guild, one appointment, `#alerts` back and recorded); `only_the_first_runs_owner_can_finish_a_half_made_installation` (other password, other username, other email: refused, no guild, no token; a second real account: refused); `a_weak_password_writes_nothing`; `two_bootstraps_at_once_one_wins`. A second run on a finished installation is in the first and in the unchanged drills (`sr-cli/tests/drills.rs` bootstrap once). **The confirm test "turned round" could not be run on the base**: it calls `bootstrap_with`, which does not exist there; the base behaviour is by reading.
- **Docs**: `docs/07-permissions-and-staff.md`; the `bootstrap` help text in `main.rs`. Sentences for ops: below.

## Proposed threat-model rows (numbered by the commander after T77)

- **A staged package left in the store for ever.** Asset: the platform bucket; actor: any application owner (resumable uploads) or a failing store/database. Abuse: complete an upload, fail or race the row update, give up or let it expire: the assembled zip (up to 32 GiB on the platform tier) stays, unreferenced, and counts against the bucket. Control: `complete` and `discard` look at the object, not the row's state; the sweep, give-up and a check that cannot be queued all delete it; at most 2 open uploads and 6 per hour per application. Residual: a delete that fails is only logged (the next sweep does not see the row again once it is `expired`); an orphan can be found with `activities/<app>/uploads/<id>.zip` keys that no open row names.
- **A bootstrap that can be raced or replayed.** Asset: the Owner account and the first login link. Actor: someone with shell access to the box, or two operators. Abuse: two bootstraps at once creating two Owners; a replay of `bootstrap` to get a fresh link for a working installation. Control: a Postgres advisory lock for the whole command (one at a time), `create_account` refuses a taken username or email, a finished installation (Staff Server and the Owner's appointment exist) or any second real account is refused, and the finishing run needs the Owner's own username, email and password. Residual: the operator with shell access and the database credentials can always edit the database.
