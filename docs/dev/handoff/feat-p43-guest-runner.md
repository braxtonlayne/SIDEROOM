## What the integrator must reconcile (43-A's contract vs mine)

All in `apps/web/src/public/guest-play/contract.ts` (types) and `session.ts` (frames).

1. **`GuestJoined` has no `capabilities`.** The runner needs the manifest's flags to refuse `ingame_voice` (gate proof) and to
   know `datachannel`. I read an optional `capabilities: string[]` from the join answer; absent, I assume
   `["guest_play", "datachannel"]`, so **the `ingame_voice` refusal cannot fire against the relay until 43-A adds the field**
   (it fires in the mocked proof). Also: `ingame_voice` is `Reserved`, so `instance.capabilities` for members omits it; the
   Share button therefore shows for such a game and the runner refuses.
2. **No nickname.** The roadmap says "random callsign or lobby-approved nickname"; 43-A's `GuestJoined` assigns the callsign
   and "guests never choose a name". The runner has no nickname field. Lobby-approved nicknames need a host approval flow on
   both sides; not built.
3. **Seats, not ids.** The relay stamps `from: <seat number>`. Guests are `g<seat>`, a member seat is `m<seat>`; room members
   speak under their user id via the 0x01 envelope. The game's host id is told by the creator's bridge (0x02). If 43-A later
   stamps ids, `lane.ts` and `envelope.ts` are the only places to change.
4. **Member seat = the link's creator only.** Only the creator knows token and key, so only their browser bridges. If that
   tab closes, guests keep playing among themselves but lose the room members. Two links on one instance are two independent
   lobbies (43-A caps five); a second creator's bridge would see the first creator's wrapped guest messages and skips them,
   but the two lobbies are not merged.
5. `publish` frames the relay drops over its budget are silent (43-A's design); Land.io's snapshot sync recovers.
6. The guest `hello` happens on `onopen`, the topic `subscribe` after `ready`; 43-A's socket accepts data without a
   subscribe, so the order is harmless. Close codes used: 4401, 4403, 4409, 4410, 4413 (constants in `contract.ts`).
7. Route matrix / OpenAPI: nothing from me. The API denylist of `check-entrance-isolation.mjs` will list `/play` and
   `/activity-instances` once 43-A's OpenAPI is merged; the `guest-play` allow entry for `/api/v1/play/` is already there
   (it shows as a stale note until then).
8. `docs/15-threat-model.md`: keep 43-A's T41, drop my stub row. `docs/inventory/21-feature-phase.md`: both branches add the
   same "Wave 43" header (identical text), merge the two items under it.

## Decisions I took (the owner may change any)

- Guests appear in the game's participant list by callsign only (D-397 allows it: they are in the game's session) so a
  host-authoritative game such as Land.io keeps their seats; they appear nowhere else.
- The runner shows a "Join the game" button instead of joining on load (link unfurlers and prefetchers must not take a seat).
- The Share button is hidden unless the game declares `guest_play` and the instance runs in a voice channel.
- The key lives in `sessionStorage` of the creator's tab only (private windows: it lives for the page's life).
- A link is not re-shown from the server (the server never has the key); a creator who loses the tab makes a new link.
