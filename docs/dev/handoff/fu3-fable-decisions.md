# Follow-up wave 3 decisions (Fable, owner-delegated, 2026-11-02), for the follow-up integrator

Scope: the six owner questions and the P32-UTL-3 limit in `docs/dev/handoff/fu-rust.md` (the defaults already merged to `main` by PR #85, `0f82ab05`). Rules applied: `docs/01-decisions-log.md` wins where it already decides (FU-1 to FU-19 included); Discord parity by default; D-385 (nothing app-side and no script on a public page); D-239 (`MANAGE_ENTRANCE` owns the entrance copy keys, `house-notes` among them); no new dependency or download (owner-only, said so where it applies). Code read at `main` (`0f82ab05`), nothing edited.

Key findings that change the picture:
- The release DM goes out through `StaffVoice::dm` (`crates/sr-server/src/staff_feed.rs`), which opens or finds the system DM and sends; it never asks the member's DM settings. The invite-card reminder does, through `ReminderGate::check(user, guild)` (`crates/sr-chat/src/cards/reminders.rs`, `SocialGate` over the social repository; `guild: None` applies only the block and the ignored/spam state). FU-3 promised "best effort under the member's DM settings (P32-UTL-3)"; the plumbing to keep that promise exists and is three lines in the route.
- The Admin "Release {title}" button (`apps/web/src/arcade/ArcadeAdmin.tsx`) calls `releaseComingSoon(s.id)` with no body, so `application_id` is unreachable from the UI; only a raw API call can set it.
- The other two entrance copy keys (`no-invitation`, `landing-note`) are rendered as restricted markdown by `EntranceMarkdown` (`apps/web/src/routes/entrance/entranceCopy.tsx`: paragraphs, headings with anchors, lists, quotes, code, bold, italic, http(s)/same-site/same-page links, never raw HTML). The Admin editor shows that same preview for `house-notes` and its hint promises "Headings get anchors such as #privacy", while the served page shows the marks as typed. The hint also says the copy appears "in place of the built-in rules, privacy, terms and credits", which was never true: it sits above them.
- `sr_core::tips::validate_tip` has two callers, `crates/sr-activities/src/arcade.rs` (manifest `tip_links`) and `crates/sr-packages/src/profile_doc.rs` (profile Links block), and both crates already pin `sha2 = "0.11"`. Base58check needs a double SHA-256 of 21 bytes; the base58 decode itself needs nothing. `sha2` is in `Cargo.lock` twice (0.10.9 for `sr-e2ee`/`sr-push`, 0.11.0 for everything else) and in no `[workspace.dependencies]` entry; `sr-core` also builds to wasm (`sr-permissions-wasm`).
- Nothing in the repository identifies a voice message by file extension: the Lounge uses the `IS_VOICE_MESSAGE` flag and `contentType.startsWith('audio/')` (`apps/web/src/lounge/msg/Attachments.tsx`), the bot SDK has no voice-message code, and the Discord bridge forwards every attachment as a signed `/cdn` link whatever its type. There is no native client. "Older clients that only look for `.ogg`" are hypothetical.
- Invite cards carry `duration_min` (15 to 720, default 120) and the reminder job closes every card six hours after its start whatever the duration (`CLOSE_AFTER_START_MS`); `closed_at` is the only "finished" mark the schema has, and the purge index already keys on `LEAST(closed_at, canceled_at)`.

Format per question: id, the decision, why, and for a change what the implementing agent does.

## 1. Release DM (FU-3)

### R1: the DM wording, and what `application_id` does
**Change: final wording below, the entry's title first, the Activity's name only when it differs; the Admin button gets a "Released as" picker so `application_id` is reachable (S, Rust and web).** The watcher opted in on the Coming Soon card's title, so that is the name they recognise; the Activity's name matters only when the Operator released it under another one. "Shipped" is trade talk and the colon-comma run-on reads oddly; other system DMs in the code are one plain sentence plus the fact ("Starting in about an hour: {title}", "The interactions endpoint of {name} was switched off."). Discord's own system DMs are one short paragraph with the link last, so the Lounge's link rendering is at the end of the text and not in the middle of a sentence. `application_id` keeps its meaning (it names the game from the candidate list, i.e. a released Activity with a declared tier) and nothing more: the release does not feature the Activity, since featuring is its own audited act with a position and blurb, and a release with no `application_id` stays valid (an entry the Operator removes because the project was abandoned still owes its watchers a word, and a game that is not an Activity at all, a cartridge for instance, has no id to give).

Exact copy (`crates/sr-api/src/routes/arcade.rs`, `release_coming_soon`), `content` only, no embed, no buttons:
- names equal, or no `application_id`: `{title} is out. You asked to be told when it was ready: it is in the Arcade now. {public_url}/games`
- names differ: `{title} is out. You asked to be told when it was ready: it is in the Arcade now as {name}. {public_url}/games`

where `{title}` is the Coming Soon entry's title and `{name}` the candidate's `name`. Compare case-sensitively after trimming; the Lounge clips nothing at this length (`clip(.., 1900)`).

Implementation:
- `crates/sr-api/src/routes/arcade.rs`: build the two strings as above; keep `application_id` in the audit payload as it is. Unit test beside the route tests: the three cases (no id, same name, different name) produce exactly those strings.
- `apps/web/src/arcade/ArcadeAdmin.tsx`: the "Release {title}" button becomes a one-row form: a `<select>` labelled `arcade.admin.soonReleaseAs` ("Released as") listing the candidates the page already fetches for the Featured section (option text `c.name`, plus the first option `arcade.admin.soonReleaseAsNone` = "No Activity (keep the card's title)"), then the button. With an Activity chosen, `releaseComingSoon(s.id, { application_id })`; without, the body is omitted as today. `apps/web/src/arcade/adminApi.ts`: `releaseComingSoon(id, body?)`.
- `apps/web/src/i18n/messages/en/fu-rust-1.ts`: `arcade.admin.soonReleaseHint` becomes: "Releasing removes the entry and sends each member who chose Notify me one direct message with a link to the Arcade, unless their direct-message settings refuse it. Choose the released Activity so the message names it, and feature it first so the link lands on it. Removing sends nothing." Add the two select strings. `i18n-audit` stays at 0.
- Vitest (`ArcadeAdmin` test): releasing with the default option sends no body; with an Activity chosen sends `{ application_id }`.

### R2: the DM honours the member's DM settings (the P32-UTL-3 limit)
**Change: check `ReminderGate::check(watcher, None)` before each send; a `Skip` or `Unknown` verdict counts as not notified (S, Rust).** FU-3 says the DM is "best effort under the member's DM settings (P32-UTL-3)"; as built it is best effort under nothing, so a member who blocked the system user or marked its conversation as spam gets a DM anyway (the block may or may not stop `messages.send`; either way the route never looks). With `guild: None` the gate applies exactly the two rules that can apply to a platform-wide notice, the block and the ignored/spam state; the per-server "allow DMs from server members" switch is about a server and the Arcade has none. `Unknown` (settings unreadable) is treated as a skip rather than a send, because a one-shot release has no retry pass and sending blind is the wrong default for a notice.

Implementation:
- `crates/sr-api/src/routes/arcade.rs`: `ArcadeDeps` gains `pub gate: Arc<dyn sr_chat::cards::reminders::ReminderGate>`; in `release_coming_soon`, for each watcher `match d.gate.check(*w, None).await { Verdict::Send => try the DM, _ => skip (debug log with the reason) }`. `ReleaseResult` unchanged (`notified` already means "delivered"); the audit payload gains `"skipped": n`.
- `crates/sr-server/src/app.rs` (~970): `gate: Arc::new(SocialGate::new(..))` built the same way as the card deps at ~1396 (share the one instance). The lounge test harness (`crates/sr-api/tests/lounge.rs`) and any `ArcadeDeps` literal in tests get a stub gate that answers `Send`.
- Test (`crates/sr-activities/tests/arcade.rs` or the sr-api route test that covers release): two watchers, one whose gate answers `Skip(Blocked)`; the result is `{watchers: 2, notified: 1}` and the DM log holds one card.

## 2. Invite cards (FU-8)

### K1: a card is finished at `closed_at` (six hours after start) or `canceled_at`
**Keep.** `closed_at` is the only "over" mark the schema has and it is what takes the buttons away; using `starts_at + duration_min` instead would purge earlier by at most six hours against a retention measured in days (default 30), and a card that is cancelled has no end to compute. The index and the job already key on `LEAST(closed_at, canceled_at)`, so nothing changes. A card that never started (cancelled before `starts_at`) is purged from `canceled_at`, which is right: nobody went.

## 3. House notes (FU-9, D-239)

### H1: the staff copy shown as escaped text, or rendered as restricted markdown
**Change: `sr-server` renders the copy as restricted markdown at serve time, the same subset the other two copy keys get from `EntranceMarkdown`, with every piece of raw HTML still escaped (M, Rust, plus the dev-server mirror and the editor hint). Amends FU-9's "escaped as text".** Three facts decide it: the Admin editor previews `house-notes` as markdown and its hint promises heading anchors, so staff write markdown and the page then shows their asterisks; the sibling keys `no-invitation` and `landing-note` are rendered, so one key out of three being plain text is an inconsistency nobody chose; and a 16 KiB legal text with no headings or lists is the one block on the page a visitor is asked to tick "I've read" for. D-385 holds: the page stays plain HTML with no script, because the rendering happens in `sr-server` and the output is static markup. No dependency: the renderer is in-house (the TS one is about 200 lines; the Rust one is the same subset), and `pulldown-cmark`/`comrak` are not in the lock and would be owner-only anyway. Until this lands, the escaped text stands; nothing is broken, only plainer than promised.

The subset (mirror `entranceCopy.tsx`, nothing more): paragraphs (blank line separated; a single newline inside a paragraph is a `<br>` as today); headings `#`, `##`, `###` rendered as `h2`, `h3`, `h4` (the page owns its one `h1`) with ids `op-<slug>` (ASCII lowercase, runs of non-alphanumerics to one hyphen, trimmed, `-2`, `-3` on a repeat; the `op-` prefix keeps staff headings clear of the built-in `rules`, `privacy`, `terms`, `image-credits`, `signin`, `notes-*` anchors); `-`/`*` and `1.` lists, one level; `>` quotes; fenced code blocks; pipe tables as the TS renderer draws them (header row, `th` scope `col`); inline bold `**`, italic `*` or `_`, code in backticks, and links `[text](href)` only when `href` starts with `https://`, `http://`, `/` (not `//`) or `#`, rendered with `rel="noopener noreferrer"` and no `target`; anything else (images, raw HTML, autolinks) is text, escaped. Every text node goes through `escape_html`.

## 4. Bitcoin legacy addresses (FU-5)

### B1: may `sha2` join `sr-core` for base58check?
**No: `sha2` stays out of `sr-core`; base58check is built without it by letting the two callers, which already pin `sha2`, hand `sr-core` the hash (S/M, Rust, no dependency change).** FU-5's condition ("where `sha2` is already a workspace dependency") was meant to keep a download and a new crate out of the follow-up; `sha2` is already built by seventeen crates and in the lock, so no download is involved, but adding it to `sr-core` is still a new edge on the crate that compiles to wasm and that every other crate depends on, which is the kind of change the binding rule leaves to the owner. It is also unnecessary: the checksum needs a 32-byte digest function, and both callers (`sr-activities`, `sr-packages`) have one. The web mirror stays shape-only for legacy addresses (the server is the authority and refuses on save; a client-side `crypto.subtle` digest is async and would reshape the validator for a check the server makes anyway).

Implementation:
- `crates/sr-core/src/tips.rs`: `pub type Sha256Fn<'a> = &'a dyn Fn(&[u8]) -> [u8; 32];` `pub fn validate_tip_with(kind: &str, value: &str, sha256: Option<Sha256Fn>) -> Result<TipKind, TipError>` and `validate_tips_with(links, sha256)`; the existing `validate_tip`/`validate_tips` call them with `None` (shape-only, as today, so the wasm build and every other caller are unchanged). `base58check_ok(addr, sha256)`: base58 decode (the 58-character alphabet, leading `1`s to zero bytes), exactly 25 bytes, version byte `0x00` (`1...`) or `0x05` (`3...`), and `sha256(sha256(&bytes[..21]))[..4] == bytes[21..]`; `bitcoin_ok` requires it for `1`/`3` addresses when a hash is given. Update the module comment (drop the "`sha2` is not a workspace dependency" sentence).
- `crates/sr-activities/src/arcade.rs` (~282 and ~540) and `crates/sr-packages/src/profile_doc.rs` (~606): call the `_with` variants with `Some(&|b| sha2::Sha256::digest(b).into())`.
- Tests in `tips.rs` with a hash closure built from a tiny test-only SHA-256? No: `sr-core` has no `sha2` even as a dev-dependency, so the vector tests live in the callers (`crates/sr-activities/tests/arcade.rs`, `crates/sr-packages` profile tests): the Bitcoin wiki vectors `1BvBMSEYstWetqTFn5Au4m4GFg7xJaNVN2` (valid), `3J98t1WpEZ73CNmQviecrnyiWrnqRhWNLy` (valid), each with one changed character (invalid), and a `bc1` case to prove the bech32 path is untouched. In `tips.rs` itself, a test with `sha256 = None` proves the shape-only path still accepts the valid vector and a test with a closure returning zeros proves the checksum path refuses it.
- `apps/web/src/arcade/tips.ts`: unchanged; its comment says legacy checksums are the server's.

## 5. Voice messages (FU-7)

### V1: WebM files stored as `audio/webm` with `.webm`
**Keep.** Nothing in the platform keys on the extension (flag and content type only, see the findings), the Discord bridge forwards links whatever the type, the bot SDK has no voice-message path, and there is no native client. Rewriting the container to Ogg on the server (a remux, not a decode, so D-201 would allow it) is real code for a client that does not exist, and storing a file as something other than what the member sent is the kind of silent change D-430-style closed formats avoid. The rule to write down so it stays true: a voice message is identified by `IS_VOICE_MESSAGE` and the attachment's `content_type`, never by its filename; a future client (bot SDK, native) follows that. If a browser is ever found that plays Ogg Opus but not WebM Opus in `<audio>`, a server-side Ogg remux (`sr_chat::voice_meta` already walks the WebM packets) is the fix, listed below as unscheduled, not owner-only.
