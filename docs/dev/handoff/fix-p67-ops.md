## 1. SEC-AUD-210: the server completes the app policy (D-682)
- New module `crates/sr-server/src/web_policy.rs` (pure functions): `PolicyInputs` (the configuration and the five variables, read once by `PolicyInputs::from_env`), `origins_from_config` (the Rust twin of `cspOptionsFromConfig`), `parse_extra_origins` / `origins_for` (validation), `merge_origins` (the merge), `sources_by_directive`, `describe_added`. `web.rs`: `WebGate::from_config` calls `from_config_with(cfg, &PolicyInputs::from_env(cfg), operator)` which calls the new `open_with_origins`; `open` and `open_with` keep their signatures (they add nothing). The merged line is the app policy and what `emulator_csp` starts from. One `info` line at start: `app policy (<path>): connect-src: ...; frame-src: ...` or `no origins added`. The header is built once; no request-time work. A new `WebError::BadCspOrigin { var, entry, why }`.
- **Which directive each kind of origin lands in:** Activities frame origin `https://*.activities.<host>` (activities on, site https, not `same_host_sandboxed`) -> `frame-src`. Voice host (each `voice.endpoints` entry whose host, with port, differs from `server.public_url`'s) -> `connect-src` as `https://h` and `wss://h` (or `http://h` and `ws://h` for a plain endpoint). `SR_PEERTUBE_HOSTS` -> `frame-src` (`https://host`) and `connect-src`. `SR_MEDIA_HOSTS` -> `connect-src`. `SR_CSP_CONNECT` -> `connect-src`. `SR_CSP_FRAME` -> `frame-src`. `SR_CSP_MEDIA` -> `img-src` and `media-src`. A directive the file lacks is created as `<name> 'self' <origins>` (the build always writes all four, so for a build's file this never happens).
- **Hosts** of `SR_PEERTUBE_HOSTS` and `SR_MEDIA_HOSTS` go through `sr_unfurl::embed::parse_hosts`, the validation the server already applies; I added no second rule (an unusable entry there is dropped silently, as before).
- **Extra variables:** each comma-separated entry must be `scheme://host[:port]`, scheme `https` or `wss` (`http`/`ws` only for `localhost`, `*.localhost`, `127.0.0.1`, `[::1]`), an optional leading `*.`; a space, quote, semicolon, path (a trailing `/` too), `@`, a keyword, a bare `*` or a bad port stops the start; the message names the variable and the entry.
- **Fixture** `apps/web/src/security/csp.fixtures.json`, 17 cases `{ name, config, extra, policy }` (+ `from: "itself"` on the last): 1 nothing set (the plain policy; the Rust test merges into this one); 2 Activities on, https site; 3 Activities on, http site (nothing); 4 Activities on, https site with a port; 5 Activities off, https site; 6 voice equal to the site (nothing); 7 voice different and secure; 8 voice different and plain; 9 one PeerTube host; 10 three PeerTube hosts (one written `https://Video.example.net:443/`); 11 media hosts; 12 a media host that is also a PeerTube host; 13 extra connect; 14 extra frame; 15 extra media; 16 everything at once; 17 a build that already holds the origins (merged into its own policy: byte-identical, nothing added). `csp.test.ts` asserts the build's function gives each `policy`; `web_policy.rs::the_merge_gives_the_policy_the_web_build_gives_for_every_fixture_case` asserts the merge gives the same sources per directive. **Same-host Activities mode is not in the fixture** (the web build has no such input): `same_host_activities_adds_no_activities_origin` covers it.
- **Voice:** the server has no `voice.public_url`; the twin of `VITE_VOICE_PUBLIC_URL` is `voice.endpoints` (what clients are handed). Empty (the embedded SFU, derived from the site) adds nothing. Owner question below.
- **What a proxy in `deploy/` does with the app policy:** nothing. `Caddyfile.prod` carries only the public policies in the generated surfaces block and says so in its comments (`The app's own policy is not in this file`); `activities.snippet` sets `frame-ancestors` on the activity hosts. I found no file in `deploy/` that sends an app policy. One real gap: `prod.yml` did not pass `SR_CSP_*` to the server container (they were only ever read by the web build), so I added the three variables to `prod.yml` and `.env.prod.example`, and to the two lists of `crates/sr-core/tests/deploy_files.rs`. The systemd route reads the process environment: INSTALL's `server.env` already holds the other variables; the upgrade notes say to put them there.
- Optional `sr-preflight` line: not done (not a few lines: the web-root check does not hold the configuration the merge needs).
